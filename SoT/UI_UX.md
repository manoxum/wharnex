# UI/UX SoT

Wharness is an engineering workspace, not a chatbot skin.

- two-column desktop workspace with chat on the left and execution intelligence on the right;
- information-dense but calm visual hierarchy;
- no decorative gradients/glow-heavy "AI" styling;
- keyboard-accessible controls, visible focus, semantic labels;
- execution state must be understandable without relying only on color;
- destructive/apply actions are visually distinct and require explicit intent;
- mobile layout stacks panels without hiding execution state.

## Appearance themes

- Wharness supports complete Light and Dark themes across bootstrap, workspace chrome, Agent, Editor, Monaco, terminal, settings, dialogs and observability surfaces. Theme selection is a local interface preference and MUST NOT alter project data.
- The default **System** preference follows the operating-system colour scheme; explicit Light/Dark choices persist across reloads, project frames and Desktop windows. A compact top-bar control provides immediate Light/Dark switching and project settings expose all three choices.
- Semantic execution and safety states retain distinct blue, green, amber and red palettes calibrated independently for each theme. Meaning MUST continue to be carried by labels, icons or shape as well as colour.
- The remote ChatGPT renderer owns its own appearance. Wharness MUST NOT inspect or mutate arbitrary remote DOM to force it to match the local theme.

## Workspace modes (v1.1)

The workspace has two first-class modes:

- **Editor**: dark IDE-style project Explorer, IDE-grade code editor, and an interactive terminal whose default target is the persistent Docker sandbox. The Explorer provides create file/folder, rename, delete confirmation, path filtering/search, refresh, collapse, context actions and reveal-current-file. A distinct Host terminal target is available only through an explicit warning/confirmation and remains visually marked while active.
- **Agent**: harness chat, plan/policy inspector, execution logs, and ChatGPT/OpenAI provider panel.

The active workspace, project path, recent workspaces, per-project choices, and local chat transcript are remembered in browser local storage. Opening or restoring a project deliberately starts on **Agent + Protected + Auto** as the operational default; the user may change execution/automation mode after the workspace is open. If the backend was restarted and the in-memory session disappeared, the frontend reopens the remembered project and creates a fresh session automatically with that safe startup profile.

The Agent **Execução** tab is an observability surface, not a stack of mini terminals. One logical command or patch owns one timeline item for its complete lifecycle: start, streamed stdout/stderr and completion are correlated by run id rather than rendered as separate rows. Output details are collapsible, the newest five output-bearing items open by default when the tab is entered, and the surface follows the tail while active as new events arrive. Each item exposes its execution date/time and duration when known; an in-flight item uses a non-colour-only animated running affordance. Host Apply/revert and self-evolution build phases are first-class execution events instead of silent side effects.


## Desktop ChatGPT composition (v1.2)

Wharness Desktop composes the real ChatGPT web surface inside the Agent inspector using a native Electron `WebContentsView`. ChatGPT transport intent is controlled from the **Wharness chat composer**, not from manual artefact cards in the ChatGPT header. Compact composer selectors represent the artefacts that will accompany the next iteration: project context ZIP, planner prompt, execution result, execution error and user-provided files. A selected selector means that artefact is part of the next ChatGPT payload. Wharness MAY auto-select an artefact when it is required by state, including forcing fresh context after another Harness chat changes the project snapshot, and selecting result/error evidence after execution or repair; required selections must not be silently deselectable.

The composer transport menu exposes two independent boolean switches: **Bundle de requisição ZIP** and **Contexto remoto em tempo real**. The global selection is the default for every chat; a chat may override both values and explicitly return to the global default. Both-on and either-only are valid. Both-off is invalid and MUST be prevented or rejected before a planner request is created. The default is tunnels-only so ordinary requests publish compact live routes and do not create/upload a duplicate request ZIP; the ZIP remains an explicit compatibility/fallback option.

The visible ChatGPT composer always receives only a concise protocol bootstrap. With ZIP or ZIP+tunnels it points to the one inbound archive and all request data remains inside that archive. With tunnels only it explains how to validate and traverse the ordered live endpoints; the prompt and files themselves remain channel resources. The UI MUST NOT paste the complete request/prompt or distribute request files across additional ChatGPT attachments.

Every ChatGPT-bound iteration MUST retain a Wharness-side reference in the local Harness transcript containing the request id, phase, bound ChatGPT conversation when known, and artefact kinds sent. Execution observability history is also retained per Harness chat across frontend/Desktop restarts so reopening a chat restores its execution timeline/log context instead of starting empty.

The native ChatGPT view occupies only the explicitly reserved viewport. It must be hidden when the tab is not active and suspended whenever a Wharness modal/overlay (including Project Context settings) is open over that area, so remote content never paints above or intercepts interaction with trusted controls.

The ChatGPT browser chrome is compact by default. Once the embedded session is confirmed authenticated, authentication is represented by a single compact status icon; login-mode controls expand only on explicit interaction or when authentication requires attention. The Desktop ChatGPT surface MUST NOT expose duplicate manual cards for copying/sending context ZIP, prompt or result bundle, and the legacy manual fallback panel is removed. Authentication exposes two first-class choices in the ChatGPT panel. **Login incorporado** keeps compatible login flows inside the sandboxed ChatGPT view; if Google is selected, the UI/backend automatically promotes the flow to secure external login rather than leaving the user on Google's embedded-browser rejection page. **Login externo (callback)** launches a real Chrome/Chromium/Brave process with a persistent Wharness-owned profile under Electron `userData` and always begins again at `chatgpt.com/auth/login`, never from an intercepted provider URL. While that browser is active the embedded ChatGPT view is hidden and the banner explains that the authenticated callback is detected automatically and the ChatGPT session is relayed back into Wharness. On success the browser window closes but its dedicated profile remains, allowing subsequent login attempts to reuse the Google account and ChatGPT session. A visible **Chrome pessoal** action opens the normal system browser with its existing personal profile/session for convenience, but it is strictly manual and session-isolated: Wharness does not inspect that profile and does not claim callback/import from it.

The Harness composer accepts a bounded set of user-selected files in Desktop manual-planner mode, whether selected through the file picker or pasted from the native clipboard. The ChatGPT surface MUST reach a loaded, network-stable state before attachment preparation, independently of whether the user has already supplied a prompt. When ZIP transport is enabled, logical prompt/context/artifact/user-file selections are packaged into one request-scoped `wharness-input-<request_id>.zip`; the complete generated planner prompt lives at `prompt/wharness-planner-prompt.md` inside that archive and MUST NOT be pasted as ordinary text. A short bootstrap in the composer points ChatGPT to that inner prompt. The refreshed project context ZIP is included inside the request archive on the first prompt for a ChatGPT conversation, whenever the concrete ChatGPT conversation URL changes, or whenever the current project snapshot hash differs from the hash last sent to that conversation. Sequential prompts to the same conversation with an unchanged snapshot MUST omit the duplicate context entry. This hash rule also refreshes a chat after another Harness chat or an external edit changes project content. Exactly one local input archive is upload-confirmed per ZIP-enabled planner turn; transient start, network, or HTTP failures retry with bounded backoff, and retry exhaustion leaves the request unsubmitted with an actionable error. In Manual automation mode preparation MUST stop before submission; the UI exposes an explicit **Confirm and send** action so the user can visually verify the selected transport payload. In project Auto mode, Wharness MUST refocus the composer and emit a layout-independent native `Enter` only after required transport preparation is confirmed plus a conservative bounded settle delay. It MUST retry focus-and-submit until the ChatGPT conversation POST is observed or the bounded attempt cap is exhausted, and the UI MUST NOT claim automatic submission before that transport confirmation. Automatic continuation begins only when the validated bundle download event is received.

User-selected Harness chat attachments are durable conversation artifacts. Before a message is sent, Desktop MUST persist a private local copy outside the target project, and the transcript stores only bounded metadata plus an opaque storage reference. Reloading or switching Harness chats MUST restore the attachment cards together with their messages. When possible, image attachments display a persisted visual thumbnail; other file types use a native file icon fallback. Opening an attachment is an explicit user action. Closing a Harness chat MUST archive it locally without deleting its transcript, ChatGPT affinity, or durable attachment directory. Only an explicit confirmed permanent deletion from the archived-chat area SHOULD remove its durable attachment directory. Legacy transcript entries that predate durable storage may remain metadata-only and MUST NOT fabricate recoverable content.

## Multi-chat conversation model (v1.2.6)

The Agent surface supports multiple Harness chats within the same workspace. A compact chat switcher must expose the active chat, create a new chat, and indicate whether each Harness chat already has a linked ChatGPT conversation. Closing a chat moves it to a recoverable archived area; that area can reopen the chat or explicitly delete it permanently with confirmation. Each chat keeps its own Harness transcript and orchestration session. Preparing a prompt, waiting on ChatGPT or executing a plan in one chat MUST NOT disable navigation to another chat or make that parallel chat unusable; asynchronous completion must remain attributed to the owning chat instead of overwriting whichever chat is currently visible.

Same-origin ChatGPT authentication redirects (`https://chatgpt.com/auth/...`) MUST remain visible in the owned embedded surface and MUST NOT automatically hide that surface by starting External mode. New views default to Embedded authentication; the user may explicitly choose External mode, and third-party OAuth that is incompatible with embedded user-agents (notably Google) still crosses the managed-browser boundary. Explicit ChatGPT `loadURL` operations MUST be serialized per owned view so redirects/reloads cannot leave competing unresolved navigations or strand the local loading fallback.

The ChatGPT panel has one-to-one conversation affinity with the active Harness chat. Selecting a linked Harness chat automatically restores its `chatgpt.com/c/...` conversation. An unlinked chat opens the ChatGPT new-chat surface, arms affinity as soon as that trusted surface is observed (even during loading), and binds the first concrete conversation URL created for it after navigation. A concrete conversation already linked to another Harness chat MUST NOT be duplicated. Existing bindings are not silently replaced merely because the user browses another ChatGPT conversation; the UI exposes an explicit rebind action. Pressing **Send** in the Harness while a different concrete ChatGPT conversation is currently open is itself explicit user intent: that send may target/rebind to the visible conversation only when it is not already owned by another Harness chat, and MUST attach fresh project context before the prompt.

When integration produces a true conflict, the Agent switches the ChatGPT tab to **Conflito GPT** and uses an auxiliary owned surface with its own persistent conversation affinity. The conflict surface receives only the focused `harness.conflict/v1` support request and fresh bounded context; it never replaces or navigates the main chat conversation. The Plan view shows the integration queue, affected paths, and conflict request. Successful resolution or explicit cancellation releases the auxiliary native view and marks its local affinity history resolved. The user can cancel the conflict by rejecting the full pending candidate; a late bundle for that cancelled request is rejected as non-pending.

For a new unbound chat, the post-submit transport waits until the concrete `/c/...` URL is stable and the owned page has finished loading before announcing the definitive binding candidate. A transient ChatGPT creation URL whose conversation id begins with `WEB:` is not definitive and is never persisted. The application controller listens for that candidate independently of the Inspector tab, reconciles missed events from every chat's Desktop state, persists it to the owning Harness chat, and confirms it with Desktop. Hiding, switching away from, returning to, or never opening the ChatGPT pane therefore MUST NOT prevent automatic binding or navigate a submitted unbound renderer back to home while its definitive URL is pending.

While an expected Auto bundle is pending, Wharness presents bounded self-recovery rather than leaving the request silently stuck. Each owned ChatGPT view disables Chromium background throttling, so hiding the native view or moving focus to Editor/Terminal does not intentionally throttle its timers. Recoverable connection/socket/DNS/proxy/TLS/HTTP2/QUIC, main-frame, allowlisted conversation-resume, HTTP 5xx, repeated DOM-probe, stuck-load or renderer failures re-hydrate the same owned ChatGPT page by reloading it; HTTP 429 instead applies a bounded retry pause. Recovery MUST distinguish a fault-only probe from a complete liveness snapshot: absent DOM/liveness fields are unknown, never evidence of silence. The Desktop tracks allowlisted in-flight ChatGPT conversation requests, and silent or ambiguous structural state MUST NOT reload or inject a processing-recovery prompt; it raises human attention while the request remains recoverable through the guarded manual action. A positively completed response with no expected bundle is reloaded once before the normal bounded delivery-continuation prompt. If the surface remains unavailable or transport retries are exhausted, automation pauses and requires human intervention rather than waiting silently until TTL expiry. Detection is language-neutral and does not read localized ChatGPT status prose.

Anti-bot/CAPTCHA/Turnstile, authentication and access-block conditions are detected only through allowlisted structural selectors/URL/title state; generated assistant prose is not inspected. While such a human gate is active, automatic reload/prompt recovery is paused so Wharness does not reset the challenge. The owning window raises operating-system attention (notification when supported plus taskbar/dock attention) and the Agent command bar keeps a persistent **Ação no ChatGPT** control. Activating that trusted control may switch to the affected Harness chat and ChatGPT tab because it is an explicit human action. The notice clears only after the structural gate is gone and the compositor is usable, or after a successful relevant transport recovery. Recovery state remains per Harness chat/request and MUST be bounded to avoid infinite reload or prompt loops.

## Project bootstrap and settings (v1.2.17)

The initial workspace surface offers three first-class project entry paths: open an existing folder through the operating-system directory explorer, create a new project below a selected parent folder, or clone a Git repository. Git clone states that recursive submodules are included. Manual project-path typing is a browser fallback, not the primary Desktop workflow.

An opened workspace exposes project settings from the top bar. The settings surface edits the context portion of `whaness.yml`: automatic pruning, include patterns, exclude patterns, and maximum per-file size. Saving reconstructs the session context immediately and keeps mandatory security exclusions visibly non-overridable. Restored sessions whose config file was removed must recreate the validated default before presenting settings; load failures show an actionable retry state rather than an indefinite loading message.

## Context transparency explorer (v1.2.17.4)

`Contexto do Wharness` is an inspection surface as well as a configuration dialog. It presents summary counts/bytes, every top-level project folder and root file with its final status, an exact searchable/filterable list of files included in the current ZIP, excluded paths with rule/reason, and the complete effective exclusion/inclusion rule catalogue. The user can rebuild the context from this surface and immediately inspect the new snapshot.

The final-context list defaults to included files because that is the payload the planner receives. Included, excluded and all-item filters remain available, with bounded incremental rendering for large repositories. Security rules are visually distinguished from optional project/heuristic rules.

The Editor Host terminal MUST expose an explicit submit affordance in addition to Enter. After Host confirmation, ordinary argv commands such as `ls`, `pwd`, `cat`, `git`, `go`, `npm` and `make` must visibly submit and return stdout/stderr. The UI must preserve the argv-only security boundary and surface policy/runtime errors in the terminal history rather than silently ignoring input.

## Harness message affordances (v1.2.18)

Every sent or received Harness transcript message displays a local date/time and exposes a compact copy action without changing the stored message content. Harness/agent responses are rendered as sanitized GitHub-flavoured Markdown so headings, emphasis, lists, tables, links and code blocks remain readable; user-authored transcript text stays literal. Legacy messages without a stored timestamp may be migrated to a bounded local fallback timestamp when loaded.

## Composer, typography and self-evolution confirmation (v1.2.26)

- The artefact selectors belong **inside the Wharness message composer**, visually adjacent to the textarea and send action. They are not a separate header toolbar.
- `Prompt` is the semantic core of a ChatGPT-bound planner turn; required/automatic artefacts must be visually distinguishable from optional user-selected artefacts without relying only on colour.
- The visible 100% typography setting is the central readable baseline, internally calibrated more generously above the former compact baseline. Settings expose a symmetric-around-100 wider bounded UI scale (40%-160%), allowing up to 60% reduction or enlargement from the central value, plus curated interface and monospace font stacks, persisted only in Wharness local UI state. The preferred pairing is Inter/Manrope for interface text and JetBrains Mono for code/logs, with system fallbacks. Small fixed UI font declarations participate in the same scale so changing the preference affects the whole workspace instead of only selected panels.
- A successful self-evolution host build MUST present a confirmation modal instead of restarting immediately. Dismissing the modal leaves a persistent compact restart-required indicator that reopens the confirmation. The pending transaction remains rollback-capable until restart is scheduled.

## Unified Agent surface and activity drawer (v1.2.39)

The Agent mode is one continuous workspace instead of a permanent Harness-chat/Inspector split. **Chat**, **Plano**, **Execução** and **ChatGPT** are first-class tabs across the same full-width surface. The Chat and Inspector components keep their state while the visible tab changes, and the native ChatGPT renderer remains suspended whenever its tab is not the visible Agent surface or a Wharness drawer overlays it.

A narrow IDE-style activity rail lives on the left edge of Agent mode. Its controls are icon-only, keyboard accessible and expose semantic labels/tooltips. **Chats arquivados** opens a drawer that lists recoverable chats and their restore/permanent-delete actions. **Project** opens a dark JetBrains-inspired, searchable, read-only project tree; choosing a file hands it to the existing Editor open/reveal flow instead of creating a second editor implementation inside Agent mode. **Planos** and **Execuções** open project-wide drawers across active and archived Harness chats: selecting a plan reuses the complete Plan detail surface, while selecting an execution exposes its command list, exit results, stdout/stderr and timing without first switching into the owning chat.

Execution actions belong to the unified Agent tab bar. The available Execute action is represented by a compact play icon with an accessible description that still distinguishes Protected sandbox execution, approval-required execution and Unprotected host-direct execution. Verified host Apply/Reject actions remain available as compact icon actions when policy/state permits them. Workspace-topbar operational badges such as self-evolution, Auto, host-direct and planner mode are icon-only; color is supplementary and every icon has a tooltip/ARIA label so status is not encoded by color alone.

## Application-owned dialogs (v1.2.37)

- Browser-native `alert()`, `confirm()` and `prompt()` surfaces are **prohibited** in Wharness product UI. Information, confirmation and textual input MUST use Wharness-owned dialog primitives so styling, language, accessibility, focus behaviour and safety semantics remain under application control.
- Application dialogs MUST present a clear title, supporting copy when needed and explicit action labels. Warning/danger confirmations MUST identify the consequence before the primary action; destructive actions MUST NOT rely on colour alone.
- Dialogs MUST be keyboard operable, trap focus while open, restore the previous focus target on close, support Escape cancellation when cancellation is valid, and expose `role="dialog"` or `role="alertdialog"` with `aria-modal="true"`.
- Every Wharness modal/confirmation/prompt MUST carry the trusted overlay-blocker marker so the Electron ChatGPT `WebContentsView` is suppressed while the dialog is active.
- New native browser dialog usage is a lint failure. Product changes that need acknowledgement, confirmation or short textual input MUST extend/reuse the shared application dialog layer instead of introducing ad-hoc browser prompts.

## Conversational semantics, planning and activity (v1.2.27)

- The composer action rail sits at the **bottom inside the composer**. Artefact/file/Plan-first controls are compact circular buttons; selected and automatic states must remain understandable through shape/marker/tooltip as well as colour.
- Project execution choices also live in that composer action rail as compact icon groups: **Protected / Unprotected** for execution containment and **Manual / Auto** for automation. The top bar may show status pills, but it MUST NOT duplicate these selectors. Self-evolution keeps Unprotected visibly disabled while preserving the existing Protected enforcement.
- Selected execution-mode icons use calm semantic palettes instead of the generic dark/lime selected treatment: **Protected** uses cool blue, **Unprotected** restrained red, **Manual** warm amber and **Auto** green. Icons, tooltips and `aria-pressed` continue to carry state semantics so colour is reinforcement rather than the only signal.
- Transcript surfaces distinguish `user`, `chatgpt` and `wharness`. Lifecycle automation text is a lightweight notice, visible ChatGPT processing/reasoning is a thought/activity surface, and neither is styled as an ordinary conversational bubble.
- Plan-first is an explicit composer mode. A planning turn cannot execute or carry patches. The resulting proposal is rendered as a plan card with reject and approve-to-implement actions. Approval creates a new direct request; rejecting it leaves the project untouched.
- While a ChatGPT-bound request is active, **Enter queues a new main request**. The queued request starts only after the active main request and every workflow/repair continuation belonging to it have completed. **Ctrl+Enter** is the explicit immediate-comment shortcut and keeps the comment bound to the active request and canonical bundle.
- Waiting main requests expose local controls to promote to comment, reorder, edit, remove and merge entries. The composer clears immediately after accepting either a main request or comment so input latency is never coupled to remote execution.
- Every implementation response still carries the protocol-level `## TODO` checklist, but the Agent UI extracts the latest checklist snapshot into a dedicated task surface near the composer and suppresses that raw section from ordinary transcript rendering.
- The Execution timeline keeps command output adjacent to its command. Streamed stdout/stderr is inserted immediately after the corresponding command event; final command payload output is only used as a fallback when streaming was absent.
- The Execution timeline groups activity by Main Request and labels each iteration as principal execution, error resolution, local information extraction, or conflict resolution. WHX lifecycle notices show their date/time and a navigable reference to the request that caused them.
- An active request exposes both **Retomar pedido** and **Cancelar pedido** where recovery is available. Cancellation ends the active chain and releases the chat for a new Main Request; it does not silently reject an already verified Protected candidate.

## Request queue, artifact inspection and resilient delivery (v1.2.30)

- Composer send is visually anchored at the right edge. Normal Enter is the main-request path; Shift+Enter inserts a line break; Ctrl+Enter (or Cmd+Enter where applicable) is reserved for a same-task comment only while a request chain is active.
- Queue state is scoped to the Harness chat. Automatic dequeue MUST be serialized and MUST NOT start the next main request while the current session has pending manual request ids, workflow/repair work, a plan awaiting completion, or a self-evolution restart handoff.
- Iteration artefact indicators are interactive controls, not decoration. When Wharness has corresponding local evidence, clicking Context, Prompt, Result or Error opens that evidence without changing transport selection.
- Generic clipboard image names MUST be uniquified before attachment de-duplication so several screenshots copied as `image.png` can be sent together.
- Desktop canonical-bundle discovery may inspect only visible/accessible affordance metadata within the trusted ChatGPT surface. Exact expected filename remains preferred; a unique newest-assistant download affordance remains a constrained fallback and the downloaded ZIP validator remains authoritative.
- If the newest assistant turn is visibly complete and no canonical bundle has been detected after a short render grace period, Desktop submits a same-request delivery continuation, re-arms the assistant baseline and keeps checking until a validated bundle arrives or the existing bounded expectation TTL expires. User comments take precedence over these automatic delivery continuations.

## Readability, resilient composer and reversible change feedback (v1.2.31)

- The Wharness composer grows vertically with multiline text until the bounded composer maximum is reached. Only the text/attachment region scrolls after that limit; the action/footer rail remains pinned inside the composer so artefact/file/Plan-first/queue/TODO icons and the send action stay visible. Composer text uses a relaxed line-height, and the send action is aligned flush to the far-right edge of the internal action row. Manual vertical resizing and per-chat height persistence remain bounded by the same composer limits.
- Chromium spell checking is enabled for the composer with Portuguese as the preferred language (`pt-PT`, then `pt-BR`) and English as fallback when the corresponding Electron dictionaries are available. The textarea advertises Portuguese language/spell-check semantics to the renderer.
- Composer draft text and user-selected composer height are persisted per project/chat. Agent and Editor workspaces stay mounted while their mode is hidden so local component state is not destroyed by a mode switch; returning to Agent restores the same draft and surfaces.
- Because Electron `WebContentsView` paints above renderer CSS, z-index alone MUST NOT be used to protect Wharness overlays. The embedded ChatGPT native view is hidden while a trusted modal, dialog, context menu or explicit overlay blocker is present, and restored only after the overlay closes. Compact error notifications are not overlays and MUST NOT suspend the native ChatGPT view.
- Request, bundle-validation and execution failures MUST keep their complete actionable detail in the Harness transcript. Any companion error popup is optional local UI state, compact, dismissible and non-blocking: it MUST NOT render the full potentially unbounded error payload or carry the ChatGPT overlay-blocker marker, and SHOULD link directly to the corresponding error entry in chat. Project settings expose a local preference that can disable these popup notifications without suppressing chat error history.
- A successful host patch application produces a compact change summary in chat. Every touched file shows additions/deletions; selecting the delta opens the raw unified diff, while selecting the filename switches to Editor and opens that path.
- A verified Protected candidate awaiting host incorporation MUST expose both **Aplicar no host** and **Rejeitar**. Apply covers every cumulatively verified pending plan. Reject requires explicit confirmation, discards the entire pending candidate, and clearly states that the host remained unchanged. A pending candidate MUST NOT block a new main request; later patches may extend it and are re-verified on top of the full candidate.
- A change summary may offer **Reverter** only for the current successfully applied Protected plan when its mutations are patch-only and therefore deterministically reversible. Reverse apply performs a check first, applies patches in reverse order, and fails closed if the working tree no longer matches. Historical summary cards MUST NOT revert a newer current plan.
- Task comments are at-most-once per queued submission attempt. Desktop serializes flushing per ChatGPT conversation and keeps short-lived idempotency/fingerprint guards so timer/manual flush races or duplicate renderer dispatch cannot submit the same guidance repeatedly. Identical deliberate comments may be sent again after the short duplicate-suppression window.
## Multi-window and bound projects (v1.2.38)

- Agent and Editor share one persistent desktop project rail at the top of each Wharness window. The rail exposes **Bind projecto**, **Nova janela**, and compact project buttons for immediate switching.
- Binding another project keeps the existing project renderer mounted but hidden. Returning to it must restore the same in-memory Agent/Editor page state and must not cancel an already running request merely because another bound project became active.
- A project already owned by another Wharness window cannot be opened concurrently in a second window. The rejection is actionable and the existing owner may be focused. The same canonical path can still be revisited inside its owning window without creating a duplicate binding.
- Inactive bound projects must suspend their native embedded ChatGPT surface so a hidden project's `WebContentsView` cannot paint over the active project. Native bounds for an embedded project include its frame offset.
- Self-evolution restart confirmation exposes three choices: **Mais tarde**, **Apenas esta**, and **Todas agora**. Because the transactional host handoff restarts the Wharness runtime, window/project layout is persisted before scheduling the handoff and restored on startup; the current-only choice prioritizes the self-evolution window while preserving the remaining window compositions.
- A canonically detected self-evolution workspace keeps a visible `WHX · AUTO-EVOLUÇÃO` badge even in the embedded multi-project layout. Its Agent activity bar exposes durable operational evidence since the latest reconciled self-evolution and an **Analisar melhorias com IA** action. Neither control is rendered for ordinary projects, even when their directory or display name resembles WHX.
- Each bound project keeps its live Agent/Editor surface mounted while switching, so its in-memory page state survives activation changes independently of other projects. A fresh process restore continues to use the existing safe Agent + Protected + Auto startup profile.

## Unified settings and remote storage accounts (v1.3)

- Project settings MUST use distinct, keyboard-accessible sections for appearance, context, Tunnel Provider, remote storage and local data instead of presenting an undifferentiated scrolling form.
- Tunnel Provider is the only remote ChatGPT transport configuration. It MUST list permanent-account providers before ephemeral compatibility providers, collect secrets only during enrollment, show whether DNS is permanent, and explain restart/rehydration behavior. Storage drivers remain configured in their own section for other purposes.
- Remote storage configuration is global to Wharness. The UI MUST support zero or more named instances, including several accounts of the same provider, and present a curated provider catalogue rather than requiring rclone terminology or manual JSON editing.
- Every instance MUST expose an explicit numeric priority and its own request-window, file-count, per-file, per-input, stored-object and storage-capacity limits. Zero is visibly documented as unlimited. Reordering instances MAY normalize priorities while preserving lower-number-first semantics.
- Drive, Dropbox, OneDrive and other OAuth-capable providers MUST expose a single connect action that launches browser authorization and returns the user to a visibly connected state. S3, WebDAV and Nextcloud MUST use provider-specific frontend forms; secret values are transient password inputs and are never re-rendered after enrollment.
- The empty instance list MUST clearly identify local ChatGPT attachments as the active fallback. The remote configuration surface MUST state the seven-day retention rule, HTTPS public-URL requirement and rclone-owned credential boundary.
- Typing `@file:` in the chat composer MUST open a keyboard-accessible search over exact files in the current eligible context manifest. Selecting a result creates a removable project-file chip and submits the canonical `@file:<<relative/path>>` reference as structured transport metadata. The composer MUST show a visible live preparation/publication state while a Tunnel Provider publishes or updates the main-request channel.
- Saving validates and atomically persists the complete pool document. Because the remote pool is constructed during backend startup, the UI MUST show that a restart is required and MUST NOT imply that the edited instances are already active.

## Chat artifact downloads and bundle explorer (v1.3)

- Every Harness chat with persisted input/output ZIPs MUST show a compact bundle-exchange strip. Each visible bundle exposes direction, canonical filename, byte size, local date/time and entry count; the full modal list retains all bundles for that session.
- Opening a bundle uses a Wharness-owned modal file explorer. It MUST support virtual folder navigation and breadcrumbs even when the ZIP omits explicit directory entries, opening bounded text files for preview, downloading an individual entry, and downloading the original bundle unchanged.
- Bundle inspection is read-only and MUST NOT extract files into the project workspace. Unsupported/binary files remain downloadable even when no inline preview is offered.
- Project settings expose global MinIO artifact retention in days. The default shown to the user is 30 days, and saving a new value applies to existing artifacts as well as future ones.
- Storage metrics include persisted MinIO artifact bytes so durable exchange storage is visible separately from local ChatGPT attachment copies and context/sandbox data.
- Artifact and Editor previews share the same safe viewer vocabulary. Text and Markdown are consumed as bounded streams; HTML is sandboxed; PDF, image, audio and video use native viewers with byte-range delivery. Office formats remain downloadable when no trusted local renderer exists. Byte-sized files are previewable, and preview eligibility MUST NOT depend on a 1 MiB all-or-nothing client read.
- The Agent activity drawer is a same-level layout column that pushes and compresses chat/inspector. It MUST NOT cover the transcript or force the owned ChatGPT view to be destroyed merely because navigation is open.
- WHX lifecycle notices render as a single-line summary by default (kind, date/time and short message) and disclose full text, request reference and actions through an explicit expansion.

## ChatGPT project and conversation lifecycle (v1.3)
