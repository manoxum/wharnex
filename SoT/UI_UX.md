# UI/UX SoT

Wharness is an engineering workspace, not a chatbot skin.

- two-column desktop workspace with chat on the left and execution intelligence on the right;
- information-dense but calm visual hierarchy;
- no decorative gradients/glow-heavy "AI" styling;
- keyboard-accessible controls, visible focus, semantic labels;
- execution state must be understandable without relying only on color;
- destructive and recovery actions are visually distinct and require explicit intent;
- mobile layout stacks panels without hiding execution state.
- left and right workspace drawers MAY stay open simultaneously; when both are open in Agent mode, the central Chat/Inspector split collapses to one surface and Chat becomes a peer tab beside Ficheiros, Plano, Execução and Engine. Closing either drawer restores the normal split without unmounting or losing the chat/inspector state.
- the fixed chat header keeps context identity compact: hash and stable Harness chat ID are not rendered as text, while one icon-only, keyboard-accessible control copies both complete values. The same context cluster also carries the current chat/session state and the icon-only chat export action.

The Agent composer exposes provider reasoning depth as **Inteligência**, with `Instantâneo`, `Médio` and `Elevado`. This control is per chat and is distinct from **Esforço**, which remains the autonomous attempt budget. Changing Inteligência persists the session choice and affects the next and subsequent provider submissions; document translation remains fixed to Instantâneo.

## Appearance themes

- Wharness supports complete Light and Dark themes across bootstrap, workspace chrome, Agent, Editor, Monaco, terminal, settings, dialogs and observability surfaces. Theme selection is a local interface preference and MUST NOT alter project data.
- The default **System** preference follows the operating-system colour scheme; explicit Light/Dark choices persist across reloads, project frames and Desktop windows. A compact top-bar control provides immediate Light/Dark switching and project settings expose all three choices.
- Semantic execution and safety states retain distinct blue, green, amber and red palettes calibrated independently for each theme. Meaning MUST continue to be carried by labels, icons or shape as well as colour.
- Interface typography MUST honor the persisted UI scale consistently. Compact chrome may use smaller labels, but operational text in tool windows, tabs, status bars and badges must remain legible at the default 100% setting; Monaco and the interactive terminal follow the same scale with editor-oriented base sizes rather than fixed micro-fonts.
- The remote ChatGPT renderer owns its own appearance. Wharness MUST NOT inspect or mutate arbitrary remote DOM to force it to match the local theme.

## Workspace modes (v1.1)

The workspace has two first-class modes:

- **Editor**: dark IDE-style project Explorer, IDE-grade code editor, and a human-only Host terminal workbench. The Explorer provides create file/folder, rename, delete confirmation, path filtering/search, refresh, collapse, context actions and reveal-current-file. Creating/opening a terminal tab is the explicit Host action; normal UI has no Sandbox/Host selector or redundant persistent Host warning.
- **Agent**: harness chat, plan/policy inspector, execution logs, and ChatGPT/OpenAI provider panel.

The active workspace, project path, recent workspaces, and per-project choices are remembered in browser local storage. Chat transcripts are durably retained by the backend; browser local storage keeps only a small synchronous cache for instant switching and MUST NOT overwrite the longer durable transcript while hydration is pending. Opening or restoring a project deliberately starts on **Agent + Protected + Auto** as the operational default; the user may change execution/automation mode after the workspace is open. If the backend was restarted and the in-memory session disappeared, the frontend reopens the remembered project and creates a fresh session automatically with that safe startup profile.

The Agent **Execução** tab is an observability surface, not a stack of mini terminals. One logical command or patch owns one timeline item for its complete lifecycle: start, streamed stdout/stderr and completion are correlated by run id rather than rendered as separate rows. Stream output does not repeat visible `[stdout]` / `[stderr]` prefixes; stderr remains semantically identified in the DOM and is distinguished with a subtle row background so failures and warnings scan faster without adding textual noise. The `execution.started` event also appends one stable, deduplicated **Execução iniciada** notice to the owning Harness transcript, including whether the target is the Protected sandbox or explicitly selected host, so a long execution never appears to be stalled before output. Output details are collapsible, the newest five output-bearing items open by default when the tab is entered, and the surface follows the tail while active as new events arrive. Each item exposes its execution date/time and duration when known; an in-flight item uses a non-colour-only animated running affordance. Host Apply/revert/restore and self-evolution build phases are first-class execution events instead of silent side effects.

The project activity rail also exposes **Erros de execução** as the structured companion to the generic execution timeline. It aggregates `harness_execution_errors` across the chats known to the open project, shows total/open/resolved/type counts and a compact failure-kind distribution, and supports status/search filters. Selecting one occurrence reveals its request/plan/root correlation, normalized cause, failed-operation logs/exit code and, when present, the GPT solution that resolved the request chain. The surface is read-only: status transitions remain owned by the execution/recovery lifecycle rather than client-side toggles, and labels must carry open/resolved meaning independently of colour.

The Harness transcript keeps high-volume output readable by default. Long ChatGPT/Wharnex Markdown is shown as an initial preview with an explicit expand/collapse control and a translucent fade that still hints at hidden content; the full source remains available and copyable. A long transcript MUST retain only a bounded message DOM window, but its virtual spacers MUST preserve the geometry of the complete transcript: dragging, wheel-scrolling, keyboard scrolling and restoring a saved scroll position update the rendered window with the native scroll position, rather than requiring page-by-page loading at an artificial boundary. At transcript open, rich offscreen entries (Markdown parsing/sanitization, attachment cards and change summaries) MUST hydrate only when they enter a bounded prefetch region around the native viewport; opening a chat MUST first leave the scroll thread responsive instead of synchronously constructing every rich entry. Applied-change cards show only a small initial set of changed-file diffs, prioritizing normative `AGENTS.md` and `SoT/*.md` entries before ordinary files, with an explicit control to reveal the remainder. After a successful Revert, that same card exposes **Repor alteração** as the inverse action while the retained reverted batch remains the latest safely restorable change; a successful restore returns the card to its applied state. Consecutive WHX notices form one visual run: only the newest notice is visible initially, preceded by a centered ellipsis control that reveals or hides the older notices without discarding their actions or provenance.

Under `harness.knowledge/v2`, every planner response in a Main Request carries the cumulative summary and knowledge catalog, and Wharnex stages those artifacts without exposing them as terminal output. After the Main Request reaches its real terminal boundary — for a change, only after successful host Apply and any required self-evolution host build — Wharnex commits the staged per-record knowledge to the database and `.wharnex/knowledge/`, then shows the compact cumulative ChatGPT summary/knowledge/recommendations/next steps, and only then a Wharnex-owned application card shows the changed-file diffs and the important commands that actually ran on the host (including the self-evolution `make build-stage` when applicable). This presentation MUST NOT depend on the renderer callback that initiated Apply: a durable `host.applied` event and hydration of a session with `last_applied_changes` both idempotently project the persisted final summary and diff card into the owning chat, so background/manual API completion and renderer restart cannot leave only an execution-status row. No dedicated final `knowledge_review` round is created for v2. Persisted pre-v2 sessions that already have `pending_knowledge_review_request_id` continue to use the legacy review gate until that request is ingested. In self-evolution, `restart_pending` remains the truthful transactional state immediately after the host build, but restart-confirmation presentation waits for the applicable knowledge commit or legacy review; the summary and applied-change card are presented before the modal opens. That modal MUST include the same applied-change diff, with per-file selection for multi-file changes, before the restart actions. It MUST also lead with the planner's own short summary of what the bundle did (see `SoT/AI_PROTOCOL.md`), so the operator deciding whether to restart the runtime reads what changed instead of reconstructing it from the patch. A change recorded before that contract carries no summary and the block is simply absent.

The Agent left activity rail exposes a read-only **Conhecimento do projeto** explorer for the opened project. It loads the latest persisted incremental knowledge catalog through the current Harness session, shows per-record version/update provenance, indexes Markdown headings as browsable topics, supports local search and manual refresh, and presents an explicit empty state before the project has retained any knowledge records. The composer exposes a compact knowledge-sharing toggle: new chats start enabled, the user can disable sharing for that chat, and a newer project knowledge revision discovered from another chat or the shared project files automatically re-enables the next request so the chat cannot silently continue from stale knowledge.

Actionable attention MUST stay out of the fixed Agent command bar as standalone labelled callouts. Host-integration retries, approval/recovery actions and ChatGPT human-action pauses are represented by the compact global alert summary. A normal verified Protected execution MUST NOT expose an **Aplicar no host** approval action; host-integration retry controls may appear only as recovery for already-authorized work. Ordinary non-alert execution and Reject controls may remain compact command-bar icons.

An expanded terminal failure notice MUST also expose its applicable recovery directly beside the evidence. Repairable execution failures show **Corrigir com GPT**, opening an optional guidance field before a manual dispatch; a previously prepared automatic repair uses the same action as a resend fallback. When the planner explicitly declared the failure non-retryable, the notice and global attention item MUST say that new evidence is required, and their shared multi-line dialog MUST reject an empty submission before any API request. Classified infrastructure failures show their truthful dedicated action instead (for example **Permitir rede e repetir** for an offline Go module cache) and MUST NOT offer a GPT source repair that cannot resolve the local condition.

The Agent MUST expose a project-level **Centro de notificações** that aggregates actionable attention from every open Harness chat, not only the currently selected chat. Its bell is a project-level action in the top workspace chrome and remains available when the center is empty. In Desktop multi-project composition, the active embedded project sends only a bounded attention summary to the same-origin WorkspaceShell, and the shell routes the bell action back to that exact project. The center includes at least host-integration retry/recovery, policy approval/block, integration conflict, interrupted execution, host dependency/toolchain blocks, ChatGPT human-action pauses, clarification requests and self-evolution restart confirmation. A durable execution intent whose status is `running` belongs to an ordinary live execution and MUST NOT be presented as interrupted merely because another chat refreshed it; after backend restart, persisted live intents are normalized to `awaiting_decision` before becoming recovery alerts. Durable clarification/blocked turns remain in conversation history after a resolving transition, but the attention projection MUST expose them only while the session is still in the corresponding unresolved state; an `applied` or `reverted` session MUST NOT resurrect an obsolete operator prompt or remedy as current attention. Clicking the bell MUST first open the bounded non-modal alert preview for the active project, showing the most relevant active alerts and their explicit actions without changing workspace mode. The preview then exposes **Abrir centro de alertas** to enter Agent and open the full notification drawer; selecting an alert may likewise navigate to its owning chat and relevant inspector surface, but navigation MUST NOT execute the alert action implicitly. Inactive chat sessions are refreshed on a bounded cadence, severity is conveyed by icon/label as well as colour, and the preview follows the shared header-popover dismissal rule for outside pointer presses and Escape.

The fixed **Ficheiros**, **Plano**, **Execução** and **Engine** surface icons belong at the far-right edge of the Agent chat switcher, after the scrollable conversation tabs; in `singlePane`, **Chat** joins the same fixed surface group. When the currently open chat owns an alert targeted at one of those surfaces, that icon MUST receive a persistent visual highlight or pulse (with reduced-motion fallback) using the alert severity; alerts from other chats MUST NOT pulse the current chat's surface icons. While a command is actively running for the current chat and **Execução** is not selected, the **Execução** icon MUST also pulse as a non-alert activity cue; selecting that surface suppresses the pulse while it is open, and command completion removes it. Conversations that do not fit in the scrollable region MUST remain reachable through a fixed overflow menu that preserves open, save/archive and the same drag-and-drop ordering model as visible tabs. Reduced-motion users receive a persistent highlight instead of animation.


## Desktop ChatGPT composition (v1.2)

Wharness Desktop composes the real ChatGPT web surface inside the Agent inspector using a native Electron `WebContentsView`. The request-bound automated surface is labelled **Engine**. A separate **ChatGPT** tab provides an ordinary, project-scoped human ChatGPT browser with no Wharness scraping, prompt submission, bundle supervision, recovery, affinity, or account automation. ChatGPT transport intent is controlled from the **Wharness chat composer**, not from manual artefact cards in the Engine header. Compact composer selectors represent the artefacts that will accompany the next iteration: project context, planner prompt, execution result, execution error and user-provided files. A selected selector means that artefact is part of the next ChatGPT payload. Wharness MAY auto-select an artefact when it is required by state, including forcing fresh context after another Harness chat changes the project snapshot, and selecting result/error evidence after execution or repair; required selections must not be silently deselectable.

The composer transport menu exposes two independent boolean switches: **Bundle de requisição ZIP** and **Contexto remoto em tempo real**. The global selection is the default for every chat; a chat may override both values and explicitly return to the global default. Both-on and either-only are valid. Both-off is invalid and MUST be prevented or rejected before a planner request is created. The default is tunnels-only so ordinary requests publish compact live routes and do not create/upload a duplicate request ZIP; the ZIP remains an explicit compatibility/fallback option.

The visible ChatGPT composer always receives only a concise protocol bootstrap. With ZIP or ZIP+tunnels it points to the one inbound archive and all request data remains inside that archive. With tunnels only it explains how to validate and traverse the ordered live endpoints; the prompt and files themselves remain channel resources. The UI MUST NOT paste the complete request/prompt or distribute request files across additional ChatGPT attachments.

Every ChatGPT-bound iteration MUST retain a Wharness-side reference in the local Harness transcript containing the request id, phase, bound ChatGPT conversation when known, and artefact kinds sent. Execution observability history is also retained per Harness chat across frontend/Desktop restarts so reopening a chat restores its execution timeline/log context instead of starting empty.

The ChatGPT mirror occupies only the explicitly reserved viewport and stops when the tab is not active. Ordinary Wharnex dialogs are non-blocking internal windows: they MUST use `aria-modal=false`, MUST keep the surrounding workspace interactive, and MUST expose close plus minimize controls visually attached to the upper-right of the window. Their primary header and explicit grip are draggable pointer handles; dragging MUST ignore interactive controls and keep the internal window bounded inside the host viewport. Minimizing keeps the window state and dragged position alive and docks a restoreable entry at the lower-right of the main host window. The real ChatGPT view lives in the browser host and project windows show only its mirror, which is ordinary DOM: dialogs, menus and overlays render above it and never suspend it.

The ChatGPT browser chrome is compact by default. Once the embedded session is confirmed authenticated, authentication is represented by a single compact status icon; login-mode controls expand only on explicit interaction or when authentication requires attention. The Desktop ChatGPT surface MUST NOT expose duplicate manual cards for copying/sending context ZIP, prompt or result bundle, and the legacy manual fallback panel is removed. Beside the operating-system browser action, the compact header exposes **Abrir no navegador interno**; it opens the linked conversation (or ChatGPT home when no conversation is linked) in a reusable detached Electron Chromium window that shares only the dedicated ChatGPT browser-session partition and carries no Wharness automation or privileged bridge. Authentication exposes two first-class choices in the ChatGPT panel. **Login incorporado** keeps compatible login flows inside the sandboxed ChatGPT view; if Google is selected, the UI/backend automatically promotes the flow to secure external login rather than leaving the user on Google's embedded-browser rejection page. **Login externo (callback)** launches a real Chrome/Chromium/Brave process with a persistent Wharness-owned profile under Electron `userData` and always begins again at `chatgpt.com/auth/login`, never from an intercepted provider URL. While that browser is active the embedded ChatGPT view is hidden and the banner explains that the authenticated callback is detected automatically and the ChatGPT session is relayed back into Wharness. On success the browser window closes but its dedicated profile remains, allowing subsequent login attempts to reuse the Google account and ChatGPT session. A visible **Chrome pessoal** action opens the normal system browser with its existing personal profile/session for convenience, but it is strictly manual and session-isolated: Wharness does not inspect that profile and does not claim callback/import from it.

The Harness composer accepts user-selected files in Desktop manual-planner mode, subject to the configured system attachment-count limit (unlimited by default) and request-bundle transport limits, whether selected through the file picker or pasted from the native clipboard. The ChatGPT surface MUST reach a loaded, network-stable state before attachment preparation, independently of whether the user has already supplied a prompt. When ZIP transport is enabled, logical prompt/context/artifact/user-file selections are packaged into one request-scoped `wharness-input-<request_id>.zip`; the complete generated planner prompt lives at `prompt/wharness-planner-prompt.md`; primary project files live directly below `context/`; `@ref` project snapshots live below `ref-context/`; `@attach` material lives below `att-context/`; and `metadata/context-sources.json` records their mapping and authority. Direct uploads and artifacts remain outside all project-context roots. A nested context ZIP is not permitted. The prompt MUST NOT be pasted as ordinary text. A short bootstrap in the composer points ChatGPT to that inner prompt. The refreshed project context directory is included inside the request archive on the first prompt for a ChatGPT conversation, whenever the concrete ChatGPT conversation URL changes, or whenever the current project snapshot hash differs from the hash last sent to that conversation. Sequential prompts to the same conversation with an unchanged snapshot MUST omit duplicate context entries. This hash rule also refreshes a chat after another Harness chat or an external edit changes project content. Exactly one logical local input archive is created per ZIP-enabled planner turn. When it fits the configured per-part bundle limit, that archive is upload-confirmed unchanged as one attachment; when it exceeds the per-part limit, Desktop upload-confirms the canonical main part plus every ordered continuation part required to reconstruct it, bounded by the configured maximum parts per request. Transient start, network, or HTTP failures retry with bounded backoff, and retry exhaustion leaves the request unsubmitted with an actionable error. In Manual automation mode preparation MUST stop before submission; the UI exposes an explicit **Confirm and send** action so the user can visually verify the complete selected transport payload, including every multipart continuation when present. In a project automatic mode (`auto` or `auto_approve`), Wharness MUST populate the owned composer without focusing it and activate its structurally located send control only after required transport preparation is confirmed plus a conservative bounded settle delay. Renderer-level native input sent to a hidden Supervisor or Worker MUST preserve the already-focused trusted local renderer, so background transport and account maintenance cannot blur either the Agent or Orchestrator composer. It MUST retry until the ChatGPT conversation POST is observed or the bounded attempt cap is exhausted, and MUST fail closed rather than sending a generic Enter to whichever element happens to be focused. The UI MUST NOT claim automatic submission before transport confirmation. Automatic continuation begins only when the validated bundle download event is received.

User-selected Harness chat attachments are durable conversation artifacts. Before a message is sent, Desktop MUST persist a private local copy outside the target project, and the transcript stores only bounded metadata plus an opaque storage reference. Reloading or switching Harness chats MUST restore the attachment cards together with their messages. When possible, image attachments display a persisted visual thumbnail; other file types use a native file icon fallback. Opening an attachment is an explicit user action. Closing a Harness chat MUST archive it locally without deleting its transcript, ChatGPT affinity, or durable attachment directory. Only an explicit confirmed permanent deletion from the archived-chat area SHOULD remove its durable attachment directory. Legacy transcript entries that predate durable storage may remain metadata-only and MUST NOT fabricate recoverable content.

For file-selection retry, a failure before any provider upload request starts and an explicit HTTP rejection remain safely retryable. A network failure or completion timeout after the upload begins is not safe to replay because ChatGPT may already hold that exact file. In that ambiguous state Wharness MUST leave the request unsubmitted, surface an actionable recovery error, and MUST NOT select the archive a second time.

## Multi-chat conversation model (v1.2.6)

The Agent surface supports multiple Harness chats within the same workspace. A compact chat switcher must expose the active chat, create a new chat, and indicate whether each Harness chat already has a linked ChatGPT conversation. Closing a chat moves it to a recoverable archived area; that area can reopen the chat or explicitly delete it permanently with confirmation. Each chat keeps its own Harness transcript and orchestration session. Preparing a prompt, waiting on ChatGPT or executing a plan in one chat MUST NOT disable navigation to another chat or make that parallel chat unusable; asynchronous completion must remain attributed to the owning chat instead of overwriting whichever chat is currently visible. Because the native Supervisor paints above React, selecting or creating another chat MUST hide the outgoing native surface at switch intent, before any asynchronous Session restoration/creation; an in-flight initial/user-directed write continues only in its hidden owned Supervisor slot. The new local chat opens immediately, but its remote Supervisor surface MUST remain deferred until that different chat's composer transaction has completed: the authenticated provider partition is shared and exposing a second surface mid-write can reflect cross-tab draft state even when the physical write target is correct. Every asynchronous preparation step MUST retain and revalidate the captured physical Supervisor entry instead of looking it up again from mutable selected-chat state. Planner workflow, repair and delivery continuations are background jobs that act on the chat's own conversation, so they run on that chat's bound Supervisor — the renderer that is already there — and MUST NOT reveal or focus it, change which Supervisor is visible, or take a slot from another chat's live request. Small account work stays on hidden Workers. Translation uses a separate hidden one-shot Translator created on demand and destroyed when its request settles. Neither path may allocate, rebind, reveal or focus a Supervisor.

Same-origin ChatGPT authentication redirects (`https://chatgpt.com/auth/...`) MUST remain visible in the owned embedded surface and MUST NOT automatically hide that surface by starting External mode. New views default to Embedded authentication; the user may explicitly choose External mode, and third-party OAuth that is incompatible with embedded user-agents (notably Google) still crosses the managed-browser boundary. Explicit ChatGPT `loadURL` operations MUST be serialized per owned view so redirects/reloads cannot leave competing unresolved navigations or strand the local loading fallback.

The ChatGPT panel has one-to-one conversation affinity with the active Harness chat. Selecting a linked Harness chat automatically restores its `chatgpt.com/c/...` conversation. An unlinked chat opens the ChatGPT new-chat surface, arms affinity as soon as that trusted surface is observed (even during loading), and binds the first concrete conversation URL created for it after navigation. A concrete conversation already linked to another Harness chat MUST NOT be duplicated. Once established, the binding is immutable for that Harness chat. Browsing another conversation does not expose a rebind action; the UI can only restore the linked conversation. Pressing **Send** while another concrete conversation is visible restores the linked conversation before transport and never redirects the request.

When integration produces a true conflict, the Agent MUST stop at an explicit choice instead of dispatching GPT automatically. The Plan view shows the integration queue, affected paths, and two primary actions: **Resolver manualmente** and **Resolver com GPT**. Manual resolution opens an app-owned three-way merge workbench inspired by IDE conflict tools: **Atual** on the left, an editable **Resultado** in the center, and **Recebido** on the right, with per-side accept actions, a base-common view, a per-file resolved state, and support for delete/modify cases. The operator may resolve every file there and apply, or resolve a subset and choose **Delegar restantes ao GPT**; manually completed paths are visibly authoritative and cannot be changed by the delegated model. Choosing GPT sends only the focused `harness.conflict/v1` support request and fresh bounded context through the same ChatGPT conversation already linked to the Harness chat. It does not create, navigate to, or supervise an auxiliary provider conversation. The user can cancel the conflict by rejecting the full pending candidate; a late bundle for that cancelled request is rejected as non-pending.

For a new unbound chat, the post-submit transport waits until the concrete `/c/...` URL is stable and the owned page has finished loading before announcing the definitive binding candidate. A transient ChatGPT creation URL whose conversation id begins with `WEB:` is not definitive and is never persisted. The application controller listens for that candidate independently of the Inspector tab, reconciles missed events from every chat's Desktop state, persists it to the owning Harness chat, and confirms it with Desktop. Hiding, switching away from, returning to, or never opening the ChatGPT pane therefore MUST NOT prevent automatic binding or navigate a submitted unbound renderer back to home while its definitive URL is pending.

While an expected Auto bundle is pending, Wharness presents bounded self-recovery rather than leaving the request silently stuck. Each owned ChatGPT view disables Chromium background throttling, so hiding the native view or moving focus to Editor/Terminal does not intentionally throttle its timers. Recoverable connection/socket/DNS/proxy/TLS/HTTP2/QUIC, main-frame, allowlisted conversation-resume, HTTP 5xx, repeated DOM-probe, stuck-load or renderer failures re-hydrate the same owned ChatGPT page by reloading it; HTTP 429 and an account-wide rate-limit gate suspend the whole provider for the duration configured in the **Policies** tab (seven minutes and thirty seconds by default, bounded from one to sixty minutes) while the affected chats stay queued and keep their attempts. Expiry does not release either pool by itself: exactly one Worker first reloads its current trusted ChatGPT URL and confirms structurally that the rate-limit gate is absent. A fresh 429 or a surviving gate opens another configured suspension; an unavailable, ambiguous, authentication or verification surface keeps claims stopped and retries the confirmation later. Only a healthy confirmation resets the provider and resumes work, without spending a task attempt. Wharness reports rate-limit suspension as provider state, never as a request that needs a person. Recovery MUST distinguish a fault-only probe from a complete liveness snapshot: absent DOM/liveness fields are unknown, never evidence of silence. The Desktop tracks allowlisted in-flight ChatGPT conversation requests, and silent or ambiguous structural state MUST NOT reload or inject a processing-recovery prompt; it raises human attention while the request remains recoverable through the guarded manual action. A positively completed response with no expected bundle is reloaded once before the normal bounded delivery-continuation prompt. If the surface remains unavailable or transport retries are exhausted, automation pauses and requires human intervention rather than waiting silently until TTL expiry. Detection is language-neutral and does not read localized ChatGPT status prose.

The rate-limit suspension scope is Worker-only: the **Policies** tab reports the durable cooldown as “Workers suspensos”, while Supervisors and Translator remain active. The **Agentes** tab additionally offers manual Worker suspension for either all ordinary Worker types or a selected set of validated task types. Account-maintenance and title types start selectively suspended by default, and the UI shows the active count/scope. This paragraph supersedes the broader whole-provider wording in the preceding historical description.

Anti-bot/CAPTCHA/Turnstile, authentication and access-block conditions are detected only through allowlisted structural selectors/URL/title state; generated assistant prose is not inspected. An authentication gate is either a `chatgpt.com/auth/*` route or ChatGPT's visible structural sign-in controls (`data-testid` `login-button`/`signup-button`) on any trusted page, because a signed-out or token-rejected session can stay on `chatgpt.com` and still render a composer. Every file upload MUST check these gates before selecting a file: a detected gate is human attention, not a transport fault, so the upload stops without consuming its bounded retries and the owning task returns provider-wide attention instead of failing into its own retries. While such a human gate is active, automatic reload/prompt recovery is paused so Wharness does not reset the challenge. The owning window raises operating-system attention (notification when supported plus taskbar/dock attention) and the Agent command bar keeps a persistent **Ação no ChatGPT** control. Activating that trusted control may switch to the affected Harness chat and ChatGPT tab because it is an explicit human action. The notice clears only after the structural gate is gone and the compositor is usable, or after a successful relevant transport recovery. Recovery state remains per Harness chat/request and MUST be bounded to avoid infinite reload or prompt loops.

## Project bootstrap and settings (v1.2.17)

The initial workspace surface offers three first-class project entry paths: open an existing folder through the operating-system directory explorer, create a new project below a selected parent folder, or clone a Git repository. Git clone states that recursive submodules are included. Manual project-path typing is a browser fallback, not the primary Desktop workflow.

An opened workspace exposes project settings from the top bar. The settings surface edits the context portion of `whaness.yml`: automatic pruning, include patterns, exclude patterns, and maximum per-file size. Saving reconstructs the session context immediately and keeps mandatory security exclusions visibly non-overridable. Restored sessions whose config file was removed must recreate the validated default before presenting settings; load failures show an actionable retry state rather than an indefinite loading message.

## Context transparency explorer (v1.2.17.4)

`Contexto do Wharness` is an inspection surface as well as a configuration dialog. It presents summary counts/bytes, file and folder views, every top-level project folder and root file with its final status, an exact searchable/filterable list of files included in the current ZIP, excluded paths with rule/reason, available size/creation/modification metadata, size-impact highlighting, and the complete effective exclusion/inclusion rule catalogue. The inventory can be ordered by name, type, size, creation date or last modification. Eligible files and folders can be explicitly included/excluded from this surface and the context is rebuilt immediately; mandatory security decisions remain visibly locked.

The final-context list defaults to included files because that is the payload the planner receives. Included, excluded and all-item filters remain available, with bounded incremental rendering for large repositories. Security rules are visually distinguished from optional project/heuristic rules.

The terminal is a full `xterm` Host PTY surface rather than a command form. Typing, paste, cursor movement, history, completion, `Ctrl+C`, interactive prompts and terminal editors flow to the PTY; ANSI output and resize events flow back continuously. The top chrome is one compact line containing terminal tabs/names, per-tab close/rename, connection status, reconnect, resize, split/detach and new-terminal actions. Normal UI does not expose Sandbox/Host selection, sandbox network/reset controls, or a separate `HOST DIRECTO` banner. Opening/creating a terminal tab is the explicit human Host gesture. Each tab persists its stable terminal id so renderer/Desktop/backend reloads reconnect the sidecar-owned PTY instead of creating a new shell; explicit tab close remains destructive. An Editor run action creates a new Host terminal tab, leaving existing PTYs alive.

## Harness message affordances (v1.2.18)

Every sent or received Harness transcript message displays a local date/time and exposes a compact copy action without changing the stored message content. Harness/agent responses are rendered as sanitized GitHub-flavoured Markdown so headings, emphasis, lists, tables, links and code blocks remain readable; user-authored transcript text stays literal. Legacy messages without a stored timestamp may be migrated to a bounded local fallback timestamp when loaded.

## Composer, typography and self-evolution confirmation (v1.2.26)

- The artefact selectors belong **inside the Wharness message composer**, visually adjacent to the textarea and send action. They are not a separate header toolbar.
- `Prompt` is the semantic core of a ChatGPT-bound planner turn; required/automatic artefacts must be visually distinguishable from optional user-selected artefacts without relying only on colour.
- The visible 100% typography setting is the central readable baseline, internally calibrated more generously above the former compact baseline. Settings expose a symmetric-around-100 wider bounded UI scale (40%-160%), allowing up to 60% reduction or enlargement from the central value, plus curated interface and monospace font stacks, persisted only in Wharness local UI state. The preferred pairing is Inter/Manrope for interface text and JetBrains Mono for code/logs, with system fallbacks. ## Non-blocking async loading and skeletons

Loading is part of the workbench interaction contract, not an implementation detail. New or materially changed pages, panels, drawers, chat tabs and heavyweight tools MUST keep navigation and already-available content responsive while slower code or data arrives.

- The application shell MUST render without awaiting optional heavyweight runtimes or remote/project data. Heavy surfaces such as editors, secondary drawers and infrequently used tools SHOULD use code splitting/lazy loading with a geometry-preserving skeleton fallback; a runtime may be warmed after the shell is interactive, but it MUST NOT gate the root React mount.
- Async data fetches MUST be started without blocking the initiating interaction. On a first load with no useful content, render a skeleton that approximates the final surface. During refresh/revalidation, keep the last valid content visible when it is safe to do so and expose a compact updating state instead of blanking the surface.
- Inspector chat tabs that depend on durable data, including Ficheiros, Plano and Execução, MUST use the same first-load skeleton/stale-while-refresh rule. Chat switching itself remains local-first: switch the tab, cached transcript and draft synchronously, then revalidate session/transcript data in the background.
- Long transcript history is the deliberate exception to animated shimmer: older entries use the existing static progressive transcript skeleton and hydrate near the viewport in bounded animation-frame work. The newest interaction window stays synchronously usable. This avoids replacing one loading stall with compositor/main-thread jank.
- Skeleton animation MUST respect `prefers-reduced-motion`. Empty states, failures and permission/policy decisions are not loading states and MUST remain explicit semantic UI rather than being hidden behind indefinite skeletons.
- A blocking wait is acceptable only when the missing result is itself a correctness or security prerequisite for the requested action. Such waits MUST be scoped to that action, not to unrelated navigation or application startup, and the reason should be documented near the implementation.

When adding or refactoring a surface, reviewers MUST treat synchronous root waits, blank loading screens, spinner-only placeholders for substantial content, and avoidable eager loading of heavyweight modules as UX regressions unless one of the explicit correctness/security exceptions applies.

While direct interaction is open, that Worker does not claim a new task.

Each follow remains bound to the task and Worker identity that opened it: opening a monitor for another task MUST NOT close, detach or replace an existing monitor for a different Worker, while opening the same Worker again MUST reuse that Worker's existing monitor window. A single Worker view MUST NOT be owned by direct interaction and monitoring simultaneously. Monitoring reparents the Worker's existing `WebContentsView`; it MUST NOT create another ChatGPT renderer, read remote content for the follow surface, or persist additional remote content. Closing one monitor returns only that Worker to its parked layout and leaves every other active monitor attached.

## Per-type task policies (see `adr/ADR-0093`)

The Policies tab of the Agents drawer and of the browser monitor opens with
**Políticas por tipo de tarefa**. Every browser task type the backend
catalog reports is listed under its category: Conversa, Orquestração, Testes
UI, Utilitários, Manutenção de chats and Títulos. A type that no category
names appears under **Outros**, so nothing is hidden.

Each category is a collapsible card. Its header shows the category name (the
description is its tooltip), colored state dots with counts, and icon-only
actions to suspend or resume the whole category. Each row shows:

- a colored state dot: **Ativo** green, **Suspenso** amber, **Cooldown** sky
  and pulsing, with the state as the dot's accessible name;
- the type's label; its code appears on hover;
- its pool, and a file icon when it sends files;
- when not active, one short line saying why and until when, for example
  "Manual · retoma às 14:30", "Por omissão · até retomar" or "Rate limit ·
  até 10:05".

Actions are icon-only (pause/play), each with a tooltip and an accessible
name.

Suspending opens an inline chooser for how the suspension ends:

- **Manual**: until it is resumed;
- **Automática**: after 15 min, 1 h, 4 h, 24 h or a custom number of
  minutes, up to 7 days.

An invalid duration cannot be confirmed. Resuming a cooldown is confirmed:
with a themed dialog in the drawer, and inline in the monitor, where a modal
would open underneath the native browser view. Compact controls MUST NOT
inherit the legacy global button sizing.

The state shown is the backend's, never inferred by the surface. The
whole-pool **Suspender Workers** control remains below as a separate,
explicitly labelled switch.

## Launcher splash output

The native "A montar o teu espaço" splash MUST show live startup output from
both stdout and stderr in readable monospace text. It starts collapsed, showing
only the most recent captured line, updated live. Expanding reveals the complete
history of the current startup, including its first lines. Older lines MUST NOT
be dropped by row-count or file-size snapshots. The private redacted startup
journal is append-only, read incrementally and removed with the splash. Per-line
redaction/bounds and bounded read/render batches remain mandatory. Both actions MUST resize the native window
to its content and
retain its dragged position. The header/title remain native drag regions while
the output controls remain interactive. Stream names MUST NOT appear as row/header
labels; stderr rows are distinguished by a red background.

The panel follows new output unless the user scrolls back and never interprets
output as markup. An icon-only copy action immediately before the expand/collapse
icon copies all currently captured, redacted output through the main process, also while collapsed. The renderer sends
only a copy intent and cannot supply arbitrary clipboard text. Failed startup
keeps the diagnostic splash available until the user closes it. Logging/display
faults MUST NOT change command exit codes or prevent startup. Credentials are
redacted before display; historical launcher logs are not replayed.
