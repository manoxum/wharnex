# Database identifiers SoT

Decision record: `adr/ADR-0084-numeric-database-identities.md`.

## Record identity

Every project-owned PostgreSQL base table, including junction and migration-ledger
tables, MUST have exactly one `id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY
KEY`. Every row MUST also have `sid text NOT NULL UNIQUE` and `uid uuid NOT NULL
UNIQUE DEFAULT gen_random_uuid()`. A newly created row receives its numeric `id`
from PostgreSQL, an application-defined stable string `sid`, and a database-generated
`uid`. Neither `sid` nor `uid` may be reassigned after creation. Sequences MUST be
advanced past the largest migrated `id` before writes resume.

`sid` is the compatibility identity. A migrated row with a former single-column
string key keeps that key byte-for-byte as its `sid`. A row formerly identified by
multiple columns gets a deterministic, unambiguous, versioned encoding of those
original values; migrations MUST detect a collision instead of overwriting a row.
An existing `uid` is preserved on rerun. `gen_random_uuid()` supplies random
UUIDs with negligible cross-table collision probability; SQL MUST enforce
uniqueness within each table, and boundary resolution MUST also use the resource
kind so even a cross-table collision cannot select the wrong record. New `sid`
values remain unique within their table and use the same typed resolution rule.

## Relationships and query boundary

Each relational reference MUST be a `bigint` column with a foreign-key constraint
to its target table's `id`. A join, filter, update, delete or ordering that follows
a relationship inside persistence code MUST use numeric `id` columns. Natural
attributes such as project paths, provider names, request labels, remote
conversation identifiers, and copied identifiers inside immutable JSON evidence
are data, not relational keys. A legacy text reference column may temporarily
remain for persisted-data compatibility, but it MUST NOT be the authoritative
relationship or the operand of a new internal join. Nullable or unresolved legacy
references MUST retain their original text and be reported during migration; they
MUST NOT be guessed into a different row or silently dropped.

An HTTP, Desktop IPC, or other external backend request MUST address a Wharnex
record with its `sid` or `uid`, never the numeric `id`. The boundary validates the
identifier and resource kind, resolves it to `id` once, then passes `id` into
persistence queries. External responses may expose `sid` and `uid`; they MUST NOT
expose internal numeric IDs as public record identifiers. Opaque identifiers owned
by another provider and ordinary non-identity strings are outside this rule.
Missing, ambiguous, malformed and wrong-kind identifiers fail closed.
A legacy `sid` may have UUID syntax; the backend checks it as an exact SID as
well as a possible UID and rejects a cross-row match as ambiguous.

## Migration and compatibility

The shared migration is `services/backend/internal/dbidentity/migration.sql` and
runs during startup after legacy schema initialization, before serving requests.
It MUST run in a transaction under a database-level migration lock. Repeated runs
MUST preserve every `id`, `sid`, `uid`, payload and relationship and MUST leave no
duplicate columns, rows, indexes or constraints. A partial run MUST roll back;
the next startup may retry safely. Existing installations, fresh installations,
and installations that have already run part of an older startup migration MUST
converge to the same schema and data. Migration MUST validate the old-to-new key
mapping, row counts, uniqueness and referential integrity before committing.
It MUST fail with actionable, non-secret context when a required source
reference has no unambiguous target. Optional historical references with no
target retain their original text and a null numeric reference until they can
be resolved. The database volume remains the authority; migration MUST NOT
reset or replace it.

Compatibility adapters may continue to accept existing string identifiers at
the external boundary and map them to `sid`. Any future public use of `uid` is
additive. An API/schema change MUST document which identifiers it accepts and
return, and tests MUST prove the numeric ID is never required from a caller.
