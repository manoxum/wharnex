# Reposição segura de alterações revertidas

Quando uma alteração Protected aplicada é revertida, conservar o batch exato de patches aplicados permite oferecer uma operação inversa explícita sem recorrer a reset/checkout destrutivo. A reposição determinística deve reaplicar os patches na ordem original e, se um patch posterior falhar, desfazer em ordem inversa qualquer prefixo já reposto antes de prosseguir para recuperação assistida.

Se a reposição direta não puder ser concluída com segurança, usar o contexto atual do projeto como autoridade e criar uma nova continuação do planner com lineage `revert_restore`. O pedido deve transportar o objetivo pós-Apply e os patches revertidos como evidência, mas não reutilizar a baseline nem o request id antigos; a solução conciliada volta a passar pelo fluxo normal de verificação Protected e Apply. Para self-evolution, a reposição deve sempre seguir este caminho de planner para não contornar a transação de build/restart.

Na UI, pedidos `revert_restore` devem permanecer semanticamente distintos de repair genérico: o cartão de alteração revertida expõe **Repor alteração**, e o bundle de recuperação é identificado no explorador como **Pedido · repor reversão** com tratamento visual próprio. Em recovery sobre uma baseline concorrente, rebasear o diff contra o snapshot atual e validar cada patch novamente; um hunk documental obsoleto não deve forçar a reutilização da baseline antiga nem descartar as mudanças concorrentes.

A validação do candidato também expôs um detalhe de qualidade no teste da timeline: ao verificar o JSON serializado, uma string delimitada por aspas simples não deve escapar aspas duplas. Esses escapes redundantes acionam `no-useless-escape`; removê-los preserva a asserção e mantém o lint limpo. Em recuperações de planner, uma falha puramente protocolar como ausência de `commit_message` deve ser corrigida com novo request/plan id sem duplicar patches que já fazem parte do candidato Protected pendente.
