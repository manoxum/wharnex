# Propostas de plano e continuações de aprovação

- No Agent, uma proposta de implementação aprovável é um turno `plan`: é não mutante e não carrega `plan.json` nem patches. `plan_first` força esse resultado, mas o mesmo deve acontecer quando o utilizador pede semanticamente para elaborar/propor/estruturar um plano enquanto o composer permanece em Direct.
- Aprovar a proposta nunca deve chamar o endpoint normal de mensagem. O backend cria uma request filha classificada `plan_approval`, com `parent_request_id` igual à request que devolveu o plano e `root_request_id` preservado, para continuar a mesma Main Request e a mesma conversa de transporte.
- Enquanto aguarda decisão, o estado é `awaiting_plan_approval`; o conhecimento candidato e o canal remoto da Main Request permanecem abertos. Rejeitar encerra esse caminho sem mutação.
- O frontend deve detetar a proposta por `last_turn.kind === 'plan'`, e não por ter sido selecionado o toggle Plan first. Depois de o backend criar a continuação de aprovação, uma falha apenas no transporte para ChatGPT não pode voltar o cartão para pending nem permitir criar uma segunda request de aprovação.
- Em repair rounds, não reutilizar um patch de proposta/aprovação construído para uma baseline antiga: rebasear sobre o contexto atual e preservar alterações concorrentes nas mesmas superfícies antes de regenerar o diff.- A regressão frontend de aprovação usa um teste de source para garantir que a proposta importada seja reconhecida diretamente por `updated.last_turn?.kind === 'plan'`. Manter essa expressão direta (sem depender do `pendingPlan` nem envolvê-la em condições auxiliares) preserva o contrato e evita que o toggle do composer volte a influenciar a deteção.
