# ADR-0012 — Canonical bundle transport and background ChatGPT input

## Status

Accepted.

## Context

Consumer ChatGPT can rename generated attachments, add visible prose despite a file-first instruction, or package otherwise valid execution metadata with harmless transport/layout mistakes. The Desktop automation also previously switched the Inspector to ChatGPT and explicitly focused the remote `WebContents`, interrupting editor and terminal work.

Wharness must remain strict about executable semantics and request correlation while being tolerant only of non-executable transport mistakes. It must also be able to prepare/submit ChatGPT input without moving the OS pointer or intentionally taking keyboard focus from trusted local surfaces. Hidden native views cannot be allowed to lose liveness merely because the user works elsewhere, and anti-bot/auth/access gates must not be treated as ordinary retryable stalls.

## Decision

1. Manual planner prompts start with an explicit `FILE_ONLY` mode and the exact canonical filename `wharness-bundle-<request_id>.zip`, prohibit visible prose, require the ZIP root layout, and require a self-check before attachment.
2. After a manual/Auto draft is submitted, Desktop records the expected request id for that chat for a bounded period. A generic ZIP download may be renamed to the canonical filename only for that active pending request. A different valid Wharness request id is rejected and never rewritten.
3. Bundle parsing may normalize only non-executable layout mistakes: one common wrapper directory, missing README documentation synthesized from already structured turn/plan text, and a referenced root-level patch basename moved logically under `patches/`. It does not invent plans, operations, commands, patches, request ids, or policy decisions.
4. Automatic ChatGPT transport does not change the visible Inspector tab and does not call `WebContents.focus()`. Synthetic input is sent directly to the remote `WebContents`; it does not move the OS pointer. Explicit user bridge actions may still focus ChatGPT.
5. Each owned ChatGPT `WebContentsView` disables Chromium `backgroundThrottling`. This changes scheduling only; the view remains hidden when local UI requires it and automatic transport still MUST NOT call `WebContents.focus()`.
6. Main-process liveness supervision may inspect only narrow structural health signals: composer availability, page visibility, processing-control presence, trusted URL/title, and allowlisted anti-bot/access selectors. It may also observe renderer lifecycle plus exact conversation transport network/HTTP status. It MUST NOT inspect generated assistant prose, cookies, storage, CAPTCHA tokens, or arbitrary DOM text.
7. Retryable renderer/network/HTTP 5xx failures use bounded reload recovery; HTTP 429 pauses before retrying. Missing surface, repeated DOM-probe/load failures, silence and ambiguous processing state escalate to a human-required state. Automatic same-request prompt injection is forbidden because it can duplicate live work.
8. A detected anti-bot/auth/access gate immediately pauses automatic recovery for that chat. The trusted shell emits OS/window attention and a persistent local action that lets the user open the affected ChatGPT surface. Automatic recovery does not reload through a human verification gate.
9. Existing protocol validation, pending-request correlation, Policy Engine checks, sandbox execution, verification, and host-apply rules remain authoritative after transport normalization.
10. Pending request ids and stable conversation affinities are the durable source for supervision. On frontend/Desktop restart, the application enumerates every live Harness chat, re-creates its owned view hidden when inactive, re-arms the exact request id, navigates to its trusted concrete conversation, and immediately probes for the expected download. While rehydrating, only the exact expected download is actionable; historical assistant turns MUST NOT be interpreted as a new terminal response. After load, Desktop records a fresh structural assistant-count baseline and waits a bounded stabilization grace before enabling terminal/recovery decisions. Re-arming the same request preserves that baseline and the rehydration gate. Bundle import is owned by the workspace controller rather than the mounted Inspector pane, so download, validation and Auto execution continue for inactive chats.
11. Download probes are single-flight per chat and independent across chats. Processing classification combines active conversation transport, assistant-turn progression, composer availability, and the processing control; no one signal is authoritative. Brief disappearance of the processing control has a settling grace. A control that remains visible without network or structural progress, or silence without positive terminal evidence, becomes an ambiguous human-attention state rather than triggering interruption or an automatic processing prompt. Concrete failures of the allowlisted conversation/resume transport receive bounded reload recovery, covering ChatGPT's localized connection-interrupted presentation without reading that text. A structurally visible response-error control receives one bounded reload; a positively terminal response without a bundle receives at most one automatic same-request delivery continuation, after which Wharness requires human attention. The user may explicitly request one request-scoped manual continuation; active conversation transport refuses it, while a possibly stale processing control requires explicit override confirmation. Structural selectors prefer stable language-neutral attributes and never depend on translated prose.
12. A downloaded bundle rejected by strict protocol validation is a different terminal state: in Auto, the backend may prepare exactly one new-request recovery with a fresh context archive and request id. This transition is durable and cannot reuse the stale bundle or its request identity. The UI dispatches the prepared request only through the owning chat and disables retry controls belonging to older failures while the replacement is pending.

## Consequences

- Generic ChatGPT attachment names no longer prevent an otherwise valid pending bundle from being imported.
- Incorrect/malicious request ids and missing executable content remain hard failures.
- The user can continue working in Editor/Terminal while automatic ChatGPT transport remains actively supervised in the background.
- Recoverable transport/render failures no longer degrade into hour-long silent waits after the bounded recovery budget is exhausted.
- Human verification cannot be bypassed automatically; Wharness surfaces it explicitly and waits for the user.
- Closing and reopening Wharness, changing tabs, or selecting another Harness chat no longer suspends an already-pending bundle download/import/execution chain.
- Consumer-web automation remains best-effort transport. Operating-system sleep, upstream outages, provider-side policy changes, unsupported/new challenge markup, and loss of network connectivity can still require recovery or human action; deterministic unattended planning should use the supported provider adapter.
