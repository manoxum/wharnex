# ADR-0053 — Inline composer directives, cross-project requests and external attachments

Status: Accepted

## Context

Wharnex had one way to point at something from the composer: `@file:<path>`. It worked by deleting the token from the sentence, adding the path to a list beside the composer, and appending a paragraph of paths after the prompt. Two things were wrong with that.

The first is that it threw away the placement. "Make the handler in @file:a.ts match the contract in @file:b.ts" says which file plays which role; two paths in a trailing list do not, and the model has to guess which is which. The operator had already expressed the relation and the transport discarded it.

The second is that a window frequently binds several projects, and there was no way to point at one. Related-project contexts were already transported — namespaced under `RELATED_PROJECTS/` — but they were reference material by construction, and the prompt told the model in as many words that its plan "may mutate only the primary project". A real workspace has contracts that span repositories: a backend route and the client that calls it, a shared type and its two consumers. Every such change meant opening the other project, re-explaining the same change in a second chat, and hoping the two halves agreed.

Both problems are about the same missing thing: a way for the operator to name something in the sentence and have Wharnex resolve it.

## Decision

**One directive grammar, written inline, for three kinds of reference.** `@file:<path>` names a file in this request's project. `@ref:<project>` names another project Wharnex has worked on before, and `@ref:<project>/<path>` names one file inside it. `@attach:<absolute path>` names a file or directory outside every project. What the operator types is canonicalized to `@{[file]…}` / `@{[ref]…}` and stays exactly where it was written. The grammar is implemented once, in `backend/internal/directives`, and mirrored by `frontend/src/lib/composerDirectives.ts` — the half that paints a chip has to agree with the half that resolves it.

Wharnex adds a bounded legend describing the notation the prompt actually used, naming any `@file` path absent from the context snapshot, and restating that referenced content is untrusted data. It does not move the markers. A malformed near-miss — `@file:/etc/passwd`, `@ref:../etc` — is left as prose, because supplying a meaning for one is precisely how a traversal turns into a resolved path.

The composer renders each directive as a chip **in place**, using an atomic embed inside a rich-text editing surface. Canonical text remains the only persisted and submitted representation; the rich document is an ephemeral projection that collapses each completed canonical marker to one embed and reduces every edit back to the same marker. Autocomplete is unified: `@file` offers this project's context files, `@ref` offers the bound projects and then, after the slash, that project's files — because naming a project and naming a file inside it are one intent at two levels of detail.

**`@ref:` in a main prompt is also the grant.** It is the only way a request acquires authority to change another project, and it is recorded durably against the root request before the planner is asked. Continuations inherit it unchanged; nothing a response returns can widen it.

Referring and changing turned out to be separate authorities, and conflating them was a mistake worth naming. The first version resolved a name only against the projects currently attached to the session, which made "is it open?" the answer to "can I point at it?". But an operator who spent last week in a repository still thinks of it by name today, and requiring them to reopen it just to write one sentence about it is asking them to restage their workspace to ask a question. So a name now resolves against **every project Wharnex has worked on before**, and a resolved project whose context is not attached has it brought in — a reference the model cannot see is not a reference at all.

What still requires the project to be open is *changing* it, and for a reason that does not weaken: the live session is what carries the Protected/Unprotected and Auto/manual modes that decide how a change reaches that host. A closed project has chosen nothing, and the Protected+Auto a fresh session would receive is a default, not the operator's decision to inherit on their behalf. The prompt names which granted projects a change cannot currently reach, so the planner spends its effort where it can land.

**A response changes a granted project through `cross_project`** in `plan.json`: one self-contained entry per project, each with the granted reference name, its own mandatory `commit_message`, its own `operations` and its own `verification`. A list of whole changes rather than a `project` tag on each operation, because a change to another project needs a commit message — it becomes that project's history — and verification that runs in that project's sandbox against that project's tree. Tagging operations leaves both of those with nowhere to live.

Authorization is fail-closed at ingestion, alongside the commit-message and impact-file contracts and for the same reason: a refusal there costs one re-request, while the same refusal after verification discards a verified candidate over something knowable before anything ran.

**Each entry executes as a derived request on its own project** — that project's Protected sandbox, its verification, its Git-native host integration, rooted on a request base captured in that project when the prompt was submitted. No new integration path was invented for the dangerous part; the existing per-project one is reused, because writing to a project is that project's authority and does not change because the patch arrived through a different chat. The target project's own Protected/Auto modes decide what happens next, exactly as they would for a request made there directly.

**External attachments are a fourth thing, and deliberately not a project.** `@attach` exists because a workspace is not the whole world: a contract lives in a sibling checkout, a vendor SDK sits outside every repository, a schema was exported to a folder somewhere. Those are things a request needs to *see*, and nothing more.

So an attachment is read-only by construction. It sits under its own `ATTACHMENTS/` namespace rather than inside the primary tree, and it may not appear in an operation, an `impact_files` entry or a `cross_project` entry — it has no root a patch could be applied against at all. That is not a restriction bolted on afterwards; it is what makes an arbitrary host path safe to admit.

The admission check is the part that earns its keep. Everywhere else in Wharnex, a path is inside a project the operator opened; here it is whatever they typed. Most of the time "they typed it, so they meant it" is a good enough reason — but not for credential stores, kernel pseudo-filesystems, or the bare home and filesystem roots whose whole subtree is everything. One typo in a composer must not be able to put an SSH key into a prompt, so those are refused outright.

Past that boundary, the selection question — what of this tree is worth sending — is the question the project's own context configuration already answers, so it is answered by the same engine and configured with the same vocabulary: automatic pruning, an include whitelist, an exclude list, the secret scan, the binary detector. The composer panel is the settings panel's context section aimed at another root, down to the per-entry Include/Exclude control. A second predicate would have been a second thing to keep in agreement with the first.

The selection travels **inside the marker** (`|+include`, `|-exclude`, `|!auto`) rather than beside it, for the same reason the markers stay inline: the prompt text is the whole state. A selection stored elsewhere is a selection that can disagree with the text it belongs to, and it would not survive a continuation or show up in a transcript.

## Refinements found wiring the composer end to end

Three things the first cut got wrong or left unfinished, surfaced by actually using the feature.

**The "every project Wharnex has worked on before" resolution had no endpoint.** `crossProjectGrantForRequest` already resolved a name against `Store.KnownProjects()` server-side, but nothing exposed that set to the composer, so the `@ref` menu kept consulting only the session's already-attached related projects — the very model this ADR said it was replacing. The fix is `Service.KnownProjects` / `GET /api/sessions/{id}/known-projects`: the read side of the exact resolution the engine performs at submit time, so a name the menu offers and a name authorization will actually accept can never disagree. This is the general shape a menu for an engine-enforced grant has to take — read from the same resolution the write path uses, never from a locally convenient approximation of it.

**One keyword per kind was not enough.** An operator reaching for "the other project" reaches for `@project` or `@reference` as readily as `@ref`; reaching for "something outside the project" reaches for `@dir` or `@attach` interchangeably. Aliases are typed spellings only — `@reference`, `@references`, `@project` for `ref`; `@att`, `@attch`, `@attche`, `@attaches`, `@attahes`, `@dir` for `attach` — drawn from one keyword table each side (Go, TypeScript) builds its regex and its menu from, so a spelling accepted by one side can never be silently rejected by the other. The canonical form written back always uses the one primary keyword, so a continuation re-parses one spelling regardless of which alias produced it. `@file` took none: it is already the narrowest, least ambiguous case, and inventing synonyms for it would only be surface area with no problem behind it.

Discoverability follows from having several keywords: typing `@` alone, before any of them is complete, now opens a menu of the directive kinds themselves. Picking one writes its canonical keyword and colon and hands off directly into that kind's own value menu — one continuous flow rather than requiring the operator to already know and spell out a directive to start one.

**A chip needed to do more than sit still.** The first cut painted each directive in place and stopped there — correct placement, but no way to inspect, change or remove one without hand-editing the marker text. Three things closed that gap, all reusing what the mirror-and-textarea architecture already had rather than adding new machinery: a small Edit/Remove/Info toolbar rendered as a child of the active directive's own chip span (so it needs no separate position tracking — the chip's rendered rect is already correct by construction), shown only for the directive the caret currently sits inside; a summary strip above the composer listing every `@ref`/`@attach` currently in the prompt as its own small chip, so the whole selection reads at a glance and clicking one moves the caret to it; and the attach include/exclude panel promoted from a box squeezed into the composer's own scroll area to a real modal, because an inventory that can run to hundreds of rows deserves the screen a modal gets rather than a 300px box wedged above the textarea.

## A fourth kind, and a click that reliably opens configuration (v1.3.10)

Two more gaps surfaced once the composer had been in real use for a while, both closed by extending what already existed rather than replacing it.

**Visible context paths had no inline spotlight, the same problem this ADR already solved for `@file`.** A file or directory could be present in the project, a related project or an external attachment without a way to say which path a particular clause should prioritize; direct uploads add the file-only case. `@see` (alias `@look`) closes that gap: it names an already-visible file or directory exactly where the sentence needs it and canonicalizes the source into the marker.

It is narrower than the other three because it never adds content or authority. Its qualified target is resolved only against content already admitted into the immutable request snapshot; the backend legend can therefore identify the exact bundle path or report it absent without reading arbitrary host state.

**A toolbar gated on the caret is not the same thing as a click that opens configuration.** The Edit/Remove/Info toolbar above answered "what is under the caret right now", which meant a chip's controls appeared reliably in the text (a click there moves the caret through it, same as any character) but not from the summary strip, where a click only moved the caret and a second, separate control handled removal — there was no path from "click the miniature" to the same Edit/Remove/Info surface a chip in the text already had. The toolbar's own positioning — absolutely placed below its anchor span, inside the mirror layer — also had no answer for a chip near the bottom of a short composer, where it could be clipped rather than flipping above.

Both are replaced by one `ComposerDirectiveConfigPopover`: positioned in JavaScript from the exact element that was clicked (`getBoundingClientRect()`, the same technique the workspace shell's own anchored popovers already use elsewhere in the frontend), flipping above its anchor when there is not enough room below. A click on a chip's text in the composer and a click on its miniature in the summary strip now open the identical popover, because both are just different callers of the same `openDirectivePopover(directive, element)`. The mirror layer itself stays exactly as inert as the ADR originally reasoned it should: nothing inside the text flow became clickable, because a clickable element inside a chip's own rendered text would give that line width the real textarea does not have, desynchronizing the two the instant a chip's line wraps. What changed is only where the resulting surface renders and what triggers it, not the non-interactive mirror the caret-passthrough depends on.

For `file`, `ref` and `see`, the popover already is the configuration surface — a status line plus Edit/Remove, since there is nothing else to configure. `attach` is still the one kind with real per-instance configuration (what a folder actually sends), so its popover's "Edit" action still opens the existing heavy `ComposerAttachmentPanel` modal rather than duplicating that panel's controls inline — the same lightweight-popover-versus-heavy-modal split the decision above already drew.

## Atomic rich-text chips replace the mirror and summary (v1.3.11)

Real use showed that painting the canonical marker behind a transparent textarea did not produce a component in the sentence; it produced textual syntax with a tinted background. The separate summary strip then duplicated that state above the input and, worse, made a partially typed `@ref:project/` look like an already selected reference while the same unfinished query remained visible below it.

The composer now follows the rich-token architecture already proven in Flowdocs. A completed canonical marker is projected to a Quill embed carrying only the bounded directive value in `data-*` attributes. The embed is `contenteditable=false` and presents a kind badge, human-readable label, compact settings icon and remove action. Incomplete typed forms remain normal text so autocomplete and continued path entry stay natural. Clicking the chip opens the existing anchored configuration popover; the settings icon on `@ref`/`@attach` opens the full selection modal directly; removing it updates the canonical text.

This changes only the editor projection, not the protocol. Drafts, submission, parsing and backend authorization still receive canonical plain text. Conversions in both directions and canonical-text/rich-index mappings are tested, including multiple directives, typed incomplete queries and literal trailing newlines. The editor reloads its rich document only for external value changes, so ordinary keystrokes do not reset its caret or undo state.

The old summary strip was removed because it treated partially typed queries as selected state and competed with the sentence-level placement of directives. A later composer evolution restores a secondary **reference-thumbnail tray**, but with a stricter contract: it is derived only from completed canonical markers and selected transport inputs, never from autocomplete text, and it cannot persist or submit state of its own. The inline chip remains the semantic placement of the directive; the thumbnail is an inspection surface. Direct uploads and content-bearing `@file`, `@ref`, `@attach`, `@chat`, `@lib`, `@todo`, `@task`, and selected next-iteration artefacts may appear there with distinct visuals, and clicking each opens the viewer appropriate to that source. `@see` is deliberately excluded because it only spotlights another admitted source and must not duplicate that source as a second miniature.

## Context-source selection and qualified `@see` (v1.3.12)

The attachment selection engine is now the shared seam for both external paths and referenced projects. An unconfigured `@ref` inherits the target project's `whaness.yml`; changing it in the composer writes request-local automatic/include/explicit-include/exclude rules into that marker and never mutates the referenced checkout. Rebuilding the workspace reapplies those rules after an automatic cross-project attach, alongside the request's external attachments, so a second rebuild cannot silently discard either selection.

`@see` now spotlights any visible path already present in the request, not only direct uploads. Its canonical payload qualifies the source as primary project, named reference, external attachment root, or upload. Project/ref/attach targets may name either an admitted file or a directory that contains at least one admitted file; the backend resolves both against the context manifests/inventories and tells the model the exact namespace path. Missing targets are reported rather than guessed. Legacy bare names remain direct uploads, which are file-only. This is a priority hint only and does not widen write authority or add bytes to the transport.

## Full-project `@file` and source-only `@see` (v1.3.13)

The composer now treats `@file` as a request-local context selector rather than as a view over the already-built context manifest. Autocomplete reads the same safe whole-project explorer the backend exposes for project browsing and offers both files and derived directory paths. When a selected path lies outside the current context snapshot, submission promotes that exact path into the primary project's request-local selection; a directory additionally contributes its subtree selector. The persisted `whaness.yml` is not changed, and the context builder still enforces mandatory exclusions, `.harnessignore`, secret detection, binary/content filtering and size limits, so discovering a path never bypasses the boundary that decides whether its bytes may enter a bundle.

`@see` is now purely a semantic spotlight over an existing transport source. Its source picker understands `file`, `chat`, `lib`, `ref`, `attach` and `upload`, while legacy `project` and bare-upload forms remain parseable for continuity. A `file`/legacy-project source resolves through the primary project context; `chat` and `lib` reuse the same artefact materialization paths as their canonical directives; references, external attachments and uploads keep their existing namespaces. The `@see` marker itself never creates another byte transport, never widens write authority and never generates a reference thumbnail — the inline chip is the whole additional UI state.

## Indexed-source `@see` autocomplete (v1.3.14)

`@see` no longer discovers a second universe of references. Its autocomplete is a projection of what the operator has already committed in the current composer: completed canonical `@file`, `@ref`, `@lib`, `@chat`, `@todo` and `@attach` markers, plus direct uploads already attached to the message. An incomplete typed fragment does not count as indexed, and another `@see` never becomes a source. This keeps the spotlight subordinate to an existing reference instead of turning it into an alternate admission path.

The source menu has a stable semantic order rather than an alphabetical one: direct attachments first, then primary-project `@file`, then `@ref`, then stored/synthetic references (`@lib`, `@chat`, `@todo`), followed by any remaining indexed source kinds such as external `@attach`. Within `@file`, `@ref` and `@attach`, autocomplete is scoped to the path already indexed: indexing a directory may expose its admitted descendants, but it does not make siblings or the rest of that source visible to `@see`.

The backend keeps the canonical parser backward-compatible, but a non-upload `@see` is resolved for the planner only when the request text also carries a matching backing directive whose scope covers the spotlight target. A hand-written or stale `@see` therefore cannot claim content that the composer did not index. Direct uploads remain the explicit exception because their admission is represented by the attachment transport rather than a second inline directive. None of this changes the original `@see` transport rule: it still adds no bytes, thumbnail or write authority of its own.

For an indexed `@ref` whose project is known but not yet attached to the session, the composer now resolves its visible file inventory on demand through the existing reference-inspection endpoint while `@see` completion is active. That gives `@see` the same file/directory drill-down affordance already available for indexed `@attach` roots without creating another transport: the inspection is only autocomplete evidence, and submission still relies on the backing `@ref` to attach/admit the referenced project context. Attached projects keep their existing manifest candidates, with inspected entries merged only as additional visible targets.

## Completed-task `@task` references

`@task:<task-id>` names one task from the current project that has already reached `COMPLETE` or `ARCHIVED`, and canonicalizes to `@{[task]<task-id>}`. It is a read-only context reference: submission materializes a bounded snapshot of the referenced task's identity, description/criteria, terminal outcome and available run/artifact metadata so the new request can understand what was done without reopening that task. The canonical marker remains inline with the sentence, following the same persisted-text/chip projection rule as other directives. Cross-project task lookup is deliberately excluded; a task id from another project is unresolved rather than implicitly granting `@ref` authority.

`@task` grants no lifecycle or mutation authority over the referenced task. It cannot release, retry, unarchive, move, re-execute or otherwise transition that task, and it never widens `impact_files`, `cross_project`, Policy or Apply authority for the current request. Follow-up implementation is always new work in the current request/task; the completed task remains immutable historical evidence. The composer and backend MUST reject or report as unresolved any `@task` target that is missing, belongs to another project, or has not yet reached `COMPLETE`.

## Consequences

- A cross-repository change is one request. The operator writes the relation once, in one sentence, and each project still gets its own sandbox, verification and integration.
- The blast radius of a granted response is bounded by something the operator typed, is visible in their own prompt, and is checked before any sandbox runs.
- A cross-project set can land partially: separate hosts mean separate integrations. Entries therefore run in order and stop at the first failure, and every outcome is reported — including the entries that were never attempted — rather than leaving the operator to infer what happened.
- A target must be open **to receive a change**; naming it never required that. The session is what carries the modes that decide how a change reaches that host, and there is no safe default to invent in its absence — but an operator can still write `@ref:` against a project they closed last week and get its content into the prompt.
- A target holding its own unfinished work refuses rather than queues. Installing a derived plan over a pending candidate would discard the operator's own work; naming the state tells them what to finish.
- The `@file` chip list beside the composer is gone. Drafts saved under the old model are folded into inline markers once, so nothing an operator had already chosen is lost.
- Naming a project no longer requires opening it, but changing one still does. That asymmetry is visible to the operator — the prompt says which granted projects are out of reach — rather than being discovered when a bundle comes back refused.
- Resolving a reference to an unattached project rebuilds the session's context to include it. That is real work on the submit path, and it is the cost of the reference meaning anything.
- An attachment can be large, unreadable, or partly excluded by its own rules. Every one of those is reported: bounds surface as truncation, refusals are named as absent, and the panel states what the selection actually admitted. An attachment that silently arrives incomplete is worse than one that never arrived.
- The composer now makes one extra request per session to list known projects. It is fetched once and cached for the session's lifetime rather than kept live, so a project opened by the operator in another window mid-session will not appear in the menu until the composer is next mounted — an acceptable staleness, unlike suggesting a name the engine will actually refuse.
- The canonical string and the rich projection round-trip exactly; the renderer never persists a second directive representation that could disagree with the protocol text.
- Qualified `@see` targets resolve through the transport they name: primary-project files/directories are checked against the resulting request context, `chat`/`lib` reuse their artefact transports, and reference/attachment/upload sources keep their existing namespaces. Missing or excluded targets are reported rather than guessed; legacy direct-upload names remain file-only.
- Every completed directive kind renders as an atomic chip in the sentence. Content-bearing directives, including same-project completed-task `@task` references, may additionally project one non-authoritative thumbnail for inspection, but `@see` never does because it is only a spotlight over another source. Incomplete autocomplete queries remain ordinary text and never appear in the thumbnail tray.
- `@task` preserves completed work as reference-only history: it can inform a new request but can never reopen or mutate the task it names.
