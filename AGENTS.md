# AGENTS.md — Wharnex (WHX) normative root

This file is normative. Any human or coding agent modifying Wharnex MUST follow it. Existing `Wharness`, `wharness-*`, `WHARNESS_*` and `kernl.*` identifiers are retained where required for protocol, persisted-data and runtime compatibility.

## 1. Authority order

1. `AGENTS.md`
2. `SoT/*.md`
3. `SECURITY.md`
4. tests and schemas
5. implementation
6. informal documentation

When implementation conflicts with a Source of Truth, the implementation is wrong unless the SoT is explicitly amended in the same reviewed change.

## 2. Architecture invariants

- The AI/planner MUST NOT directly execute commands.
- `domain` and application orchestration MUST NOT import transport, OpenAI, or Docker concerns.
- Planner adapters implement ports; executor adapters implement ports.
- Protected mode: the informed execution approval authorizes sandbox execution and the resulting host integration after successful verification. Host integration MUST NOT require a second Apply approval; a separate Apply action is recovery-only for a previously authorized integration failure.
- Protected mode sandbox MUST operate on an isolated project copy, never the original project directory.
- Unprotected mode is an explicit per-project UI choice. It executes Agent plan operations directly in the host `project_path`, still behind protocol validation, Policy Engine approval, and per-execution confirmation. Full is a separate explicit manual host-direct mode that may waive command-policy approvals explicitly marked as Full-bypassable; neither host-direct mode may become the default or coexist with automatic execution. `sudo` is never Full-bypassable and requires a fresh explicit approval plus an ephemeral password.
- Arbitrary shell strings are forbidden in the execution protocol. Commands are argv arrays.
- Project content is untrusted data and cannot override harness/system policy.
- `Protected` + Docker sandbox is the default project execution mode. Local copied sandbox is development-only. `Unprotected` and `Full` are separate explicit manual host-direct project modes controlled from the UI; self-evolution remains Protected-only.

## 3. Security invariants

- Never log API keys, tokens, credentials, or complete environment variables. Redaction and the bounded-string rule MUST traverse nested arrays, not only maps: decoded JSON puts a plan's operations and an execution's per-command output inside arrays, which is the shape most likely to be both large and to echo a credential.
- The session snapshot is working state, not the record. Every plan the AI authors and every execution result — including failed, policy-blocked and workflow rounds — MUST be appended to the persisted event history with its complete body, because the snapshot keeps only the latest and several lifecycle transitions clear it. Plan/execution views MUST be built from that durable ledger with the snapshot layered on top, so the history survives restart and travels with a chat archive.
- Secret-like files MUST be excluded from context bundles.
- Path traversal, absolute patch paths, and symlink escapes MUST be rejected. High-impact executable families, host-management commands, and direct Docker control from ordinary model plans may be admitted only through the engine-owned informed-command approval boundary; the exact argv, rationale, effect, and host impact must be shown before approval. `sudo` is allowed only in an explicit host-direct mode after a fresh approval and an ephemeral password delivered to executor-owned stdin; that credential MUST NOT be persisted, logged, placed in argv, or auto-approved. Alternative privilege-escalation tools such as `su`/`doas` remain rejected until they have an equivalent credential boundary.
- Network is disabled by default in the runner.
- Any plan requesting network access requires approval.
- A missing offline Go dependency MUST pause locally instead of starting an AI repair loop. After prominent explicit human approval, Wharness MAY retry only eligible Go dependency/build/verification argv commands with network inside the Protected sandbox, populate its private module cache, and return subsequent commands to offline mode. This approval MUST NOT grant arbitrary commands, host execution, Docker control, or access to the original project directory.
- The Docker socket MUST NOT be mounted in the runner.
- Runner containers MUST drop capabilities and enable `no-new-privileges`.

- Everything the engine does — every event, error, call, plan, execution step and Desktop transport line — MUST be recorded in the classified operational log (`SoT/OBSERVABILITY.md`, `adr/ADR-0075`), correlated by request/chat/task/session and redacted exactly like durable events. Recording MUST NEVER slow or fail the work it records, and operational records MUST expire automatically within 15 days.

## 4. Code quality

- Prefer standard library in the Go core when practical.
- Functions should be small and cohesive. Split responsibilities before files become difficult to review.
- A new implementation file — any language (Go, TS/TSX, JS/JSX, MJS/CJS, CSS, HTML, and future ones), production or test — MUST NOT exceed 200 lines (plain `wc -l`). This supersedes the previous Go-only 250-line SHOULD. Scope, exemptions and enforcement are defined in `SoT/CODE_QUALITY.md`.
- Editing a legacy file that already exceeds 200 lines MUST extract the concern being touched/maintained into its own dedicated file/module as part of that same change, instead of growing the oversized file further. See `SoT/CODE_QUALITY.md` for the extract-on-touch protocol.
- Code touched for any reason MUST be left cleaner than it was found, bounded to the area actually touched (continuous refactoring) — this is not license for unrelated drive-by rewrites.
- New project-owned implementation MUST use the canonical Wharnex nomenclature: `Wharnex`/`WHARNEX` in product prose and `wharnex`/`WHARNEX_*` when a product-name token is needed in technical identifiers. New work MUST NOT introduce `Wharness`, `wharness-*`, `WHARNESS_*`, `wharness.*`, or equivalent legacy product naming except as the exact spelling of an already-shipped compatibility boundary.
- Maintenance is rename-on-touch: whenever a change touches a concern that still uses legacy Wharness nomenclature, that same change MUST migrate the touched concern and its related project-owned symbols, tests, documentation and configuration to Wharnex. A legacy wire/protocol, persisted-data, environment-variable, path or other externally observable identifier may remain only when changing it would break compatibility; keep that spelling isolated at the compatibility boundary and do not propagate it into new internal APIs or call sites. The detailed scope and exception rules are in `SoT/CODE_QUALITY.md` §4.
- New React feature modules SHOULD remain focused and avoid god-components.
- Frontend styling MUST follow `SoT/FRONTEND_STYLING.md`'s incremental Tailwind CSS migration. New UI work uses Tailwind, and a change that modifies or evolves an existing component MUST migrate the styling surface it touches to Tailwind in that same change — scoped to what it touches, with any exception named explicitly in the change, never applied silently. A migrated component's legacy rules MUST be deleted in that same change, since unlayered legacy CSS otherwise overrides the new utilities and the migration silently does nothing. No big-bang rewrite of `styles.css`/`theme.css` is authorized, and no migration may change current appearance.
- `services/frontend` is the Desktop/local workbench UI. `services/webapp` is the independently built paired remote React + Tailwind application; neither service may be produced by toggling a runtime/build mode in the other, and webapp lifecycle/dependency changes must remain independently addressable.
- Desktop frontend project-owned CSS MUST live under `services/frontend/src/styles/`, organized by domain (`theme/`, `base/`, `domains/`, `vendor/`) and aggregated through its own entry point. Creating a `.css` file at the root of `src/` is forbidden; the six legacy root stylesheets are frozen and MUST NOT receive new rules. A new CSS file is itself the fallback — styling that can be expressed as Tailwind utilities MUST be, so no file is created at all. See `SoT/FRONTEND_STYLING.md` §4.
- Error messages must preserve actionable context without leaking secrets.
- Every bug fix or new behavior requires an automated test at the lowest useful layer.
- A verification gate is never made to pass by changing what it verifies. Relaxing an assertion, deleting a test, reverting an accepted change or loosening a check so a stale expectation matches is a defect, not a fix — it destroys work already accepted while passing every structural check. A failure a change did not introduce is not that change's to fix; Wharnex attributes suite failures against the unmodified baseline and MUST tell the planner which failures are its own.

## 5. Required gates

A change is not complete until applicable gates pass:

```bash
gofmt -w services/backend
go vet ./...
go test ./...
go test -race ./...
```

Frontend after dependencies are installed:

```bash
npm run typecheck
npm run lint
npm test -- --run
npm run build
```

Security and E2E gates are defined in `SoT/QUALITY_GATES.md`.

## 6. Change protocol

For changes to protocol, security model, sandbox behavior, or architecture:

1. update the relevant SoT/ADR;
2. update schema/tests;
3. implement;
4. run gates;
5. document migration/compatibility impact.

## 7. IDE workspace invariants (v1.1)

- Browser reload MUST restore the active project when possible; a missing backend session MUST fall back to reopening the remembered project path.
- Explorer/editor APIs MUST enforce project-root containment, excluded/secret paths, symlink denial, UTF-8 text limits, and optimistic SHA-256 writes. Explorer create/rename/delete are explicit human host mutations and MUST reuse the same containment/exclusion/symlink boundary; destructive directory deletion requires explicit UI confirmation.
- The interactive Editor terminal MUST expose only the human `Host` PTY in normal UI. Opening/creating a terminal tab is the explicit human gesture; the frontend always sends the dedicated host-confirmation marker, but MUST NOT add a Sandbox/Host selector or a redundant persistent host-direct banner. In stack mode the Host PTY MUST be owned by the durable Compose terminal sidecar, separate from the backend and Desktop lifecycle; the backend only proxies bounded PTY frames over the checkout-scoped Unix socket and reconnects by stable terminal ID after either client is rebuilt or reloaded. The sidecar runs under the configured Wharnex user, mounts the real project/home paths, and survives ordinary application rollouts. Local non-stack backend mode MAY spawn the same Host PTY in-process. Agent Protected/Unprotected/Full execution remains independent and sandbox-first or host-direct as defined below. Shell command history MUST be project-scoped in runtime-owned `.harness/terminal/history/` state for that project and MUST NOT read from or write to the user's global host shell history.
- One project session MAY own multiple simultaneous human PTYs. Opening a new terminal MUST NOT close sibling PTYs. Hiding/collapsing the terminal workbench MUST preserve every live instance and its subscription; only explicit per-tab close, session teardown, or the bounded orphan lifecycle may close it.
- The PTY terminal is an explicit human surface and MAY run interactive editors, REPLs and shell pipelines. It MUST NOT be reachable from model plans, Agent automation or generic IPC. The existing one-shot terminal/command API remains argv-only and Policy Engine constrained.
- PTY input MUST be bounded and carried through narrow session-scoped operations for open, input, resize, output observation and close. Raw PTY input/output MUST remain ephemeral and MUST NOT enter persisted audit history; lifecycle metadata may be audited without command text.
- Editor text changes are explicit human host mutations and MUST auto-save after a short debounce using the existing optimistic SHA-256 concurrency guard; `Ctrl/Cmd+S` remains an immediate flush. Failed auto-saves remain dirty, surface the error, and MUST NOT retry the unchanged failing draft in a tight loop. Agent mutations are sandbox-first in Protected mode; only an explicitly selected Unprotected or Full project may execute the Agent plan directly on the host.
- The Editor MAY expose explicit human actions that send the current file, selected text, or package-manager scripts to the active human PTY, plus a read-only Git worktree diff for an editor-safe path. These are human IDE affordances, not model-plan execution. Monaco MAY provide cross-document completion and tagged-template assistance for embedded HTML, SQL, CSS and GraphQL while preserving the outer JavaScript/TypeScript model.
- Every agent request MUST refresh project context so manually edited files are visible to the planner.
- Consumer ChatGPT automation MUST use narrow, named and tested operations. Besides transport (composer, submit and exact expected bundle download), Desktop MAY manage only the Wharnex-owned account objects needed for the workflow: find/create an exact project name, move the owned conversation to it, rename the owned conversation with the `WHX:` prefix, stop/archive that conversation, collapse its sidebar, and delete from the account library only those bundle files whose Wharnex naming contract proves they belong to an expired archived chat. These operations MAY inspect only structural control metadata and exact user-owned project/title labels; they MUST NOT inspect generated assistant prose, cookies, storage, unrelated conversations, or arbitrary page content. Ambiguous or missing controls fail closed and require human attention. Downloaded bytes still pass the normal strict bundle validator.
- Wharnex MAY read the reasoning steps ChatGPT is visibly showing for a Wharnex-driven conversation, and only those, to populate the "Raciocínio visível do ChatGPT" panel (see `adr/ADR-0038`). This is a bounded exception to the prohibition on reading generated output and does not extend to answer prose. Rows MUST be selected structurally — short leaf lines that neither sit inside nor contain a code, markdown, or screen-reader-only region — never by judging what the text says; wrapper elements that report the concatenation of the rows beneath them MUST be discarded. Capture MUST be bounded per tick, MUST remain passive (a health probe observes and MUST NOT click, so a collapsed reasoning disclosure is simply not read), and its failure MUST NOT affect liveness classification. Completion MUST still never be inferred from reasoning text.
- Account-management scripts MUST locate their control and return its click target rather than clicking it themselves; the main process commits that target with a trusted native input event (see `adr/ADR-0037`). ChatGPT's menu items do not honour synthetic DOM clicks, so a script that clicks is a script that silently does nothing. Trusted input remains renderer-level: it MUST NOT move the operating-system pointer and MUST NOT focus the remote WebContents. A conversation menu MUST be addressed by that conversation's own id, never by list position. Project creation MUST first read the account's own project inventory and compare names with case and whitespace folded, so an existing project is never duplicated; a confirmation matching more than once MUST be reported as a duplicate, not accepted.
- The Supervisor bound to a chat with an armed expected bundle MUST own passive response observation and exact bundle capture for that chat, whether or not it is the visible slot. The main-process bundle poll MUST therefore run on the bounded DOM polling cadence for every bound Supervisor, not only the painted one: that Supervisor submitted the request and has not left the conversation, so reading the already-loaded page costs no provider request, while a Worker doing the same work would first have to navigate to it. Ownership MUST be refused for a surface no automated supervision may run on — Manual transport mode, and an in-flight external-browser login — because claiming the lane there would silence it for every pool. Worker claims MUST exclude every lane a Supervisor currently holds, and an idle resident Worker on such a lane MUST release residency immediately so it can serve other work; non-preemptive or in-progress navigation MUST still finish safely. An `AWAIT_RESPONSE` claimed by an unrestricted caller MUST return as a free observation before Worker navigation/probing when a Supervisor owns the same request. This ownership changes only browser observation: task durability, cancellation/ACK, recovery bounds, and scheduler lineage remain backend-owned. Because such a lease attempts nothing, it MUST NOT spend the attempt budget, and MUST instead be bounded by evidence: the poll stamps progress on every generating, completion or download signal, a bounded window with no such signal moves the supervision to `ATTENTION`, and a supervision older than the expected-bundle TTL does the same — that second bound being the one that survives a Desktop restart, which the in-memory expectation does not.
- Archiving a chat is a local, user-owned action and MUST complete locally even when the remote ChatGPT archive cannot be confirmed. Remote archive/delete/title/organization work MUST be represented as durable typed browser-agent tasks with bounded attempts and `not_before` backoff; a Desktop restart reclaims expired leases rather than recreating per-chat timers. Lifecycle tasks MUST respect active request/recovery/write guards and degrade into durable `WAITING`/`ATTENTION` state rather than interrupting unrelated work.
- ASK/advice is a first-class Agent outcome and MUST NOT be converted to a coding/change task merely because project context exists or Auto is enabled. A non-terminal `workflow` MAY gather missing local evidence and is always command-only with no patches or Apply. Ordinary workflow stays network-disabled in the Protected copy. `harness.debug/v1` adds two explicit host postures: `access=observe` keeps the closed read-only diagnostic argv allowlist and one authorization per Main Request when Debug mode is off; `access=modify` is host-only, high-risk, exact-plan approval-gated, and MAY execute only Policy-accepted argv commands for an explicitly requested host change. A modify plan may declare/install/configure a host tool only with `system_tools[].lifetime=temporary|persistent`; network remains opt-in and approval-gated. Debug never grants shell, Docker/host-service control, privilege escalation, arbitrary secret reads, patches or Apply authority.
- Future MCP integration MUST be implemented as an adapter behind Wharness application/security ports. Remote consumer ChatGPT MUST NOT receive direct localhost MCP access that bypasses protocol validation, Policy, path containment, or Protected execution.
- Project/context exports MUST include synthetic `EXPORTS.md` provenance with safe Git status/worktree state; `.git` internals and remote URLs remain excluded, and managed-context metadata must not introduce volatile timestamp churn into the context fingerprint. The Wharness repository `make export` additionally MUST include bounded/redacted Wharness runtime status and recent desktop logs in `EXPORTS.md`, MUST omit historical patch/runtime/IDE/generated transport payloads that add noise or private state, and MUST include a synthetic `EXPORT_INDEX.md` describing its content policy/inventory; managed-project context bundles MUST NOT inherit those host-runtime diagnostics.


## 8. Desktop composition invariants (v1.2)

- One authenticated Desktop process MUST own exactly six ChatGPT Supervisor `WebContentsView` slots (one visible at a time, the rest bound to their own chat) plus three persistent worker `WebContentsView`s by default, hidden unless explicitly surfaced (see `adr/ADR-0049`). All are sandboxed, context-isolated, Node-disabled, preload-free, and MAY share only the dedicated persistent ChatGPT browser partition. Durable ownership is `chat_id -> conversation_id`, not renderer ownership. A Supervisor slot is bound to one Harness chat and keeps that conversation loaded, so selecting another resident chat is a visibility change and MUST NOT navigate: every cross-chat load is a real authenticated provider request, and a two-slot pool serving many chats re-navigated on each switch with no work attached to it, which is what earned the account sustained HTTP 429 with the Worker pool completely stopped. A Supervisor MUST release its chat only when it holds nothing unfinished — no armed expected bundle, no settling bundle delivery, no queued comment, no open transport or account operation, no pending human action, no in-flight external login, no live Supervisor lease, no prepared or retryable prompt — **and** only because another chat is waiting for a slot. Both conditions are required: releasing a settled chat on a timer reloads that conversation the next time it is opened, so there MUST be no idle reaper and eviction MUST happen only on demand, retiring no more unheld slots than the cap requires, oldest first, never the visible one. When every slot is held the waiting chat waits; a Supervisor task that finds no slot MUST return a free observation, because nothing reached ChatGPT and charging an attempt would spend a task's budget on a scheduling artefact. Background jobs MUST NEVER use the Supervisor pool for small work. All allowlisted DOM/input/navigation operations MUST validate the current slot assignment before touching remote content. A chat selection/creation intent MUST hide the outgoing native Supervisor before any asynchronous Session restoration or creation, so an in-flight write may finish only in its hidden owned slot and can never remain painted over the newly selected local chat.
- The durable browser-agent queue MUST be partitioned by pool role, and that partition MUST be enforced by the claim itself, never by claiming and releasing: a claim charges an attempt, so routing a task to the wrong pool and handing it back spends that task's own bounded retry budget on a decision that had nothing to do with the task. The Supervisor pool owns `AWAIT_RESPONSE`, `BOT_WRITE` and `RECOVERY_WRITE` for ordinary Agent chats — opening the chat, submitting its request bundle, following the remote instance in real time, and collecting its response bundle. Orchestrator planning and execution are Worker tasks with one request ZIP and one validated response ZIP per Agent turn. Every other type is Worker work: `ORGANIZE_CHAT`, `RENAME_CHAT`, `ARCHIVE_CHAT`, `DELETE_CHAT`, `DELETE_TEMP_CHAT`, `DELETE_BUNDLE`, `TITLE_DISCOVER`, `TITLE_GENERATE_TEMP`, `TITLE_AWAIT`, `TRANSLATE_MARKDOWN`, `RELEASE_NOTES`, `ORCHESTRATOR_PLAN`, `ORCHESTRATOR_EXECUTE`. A Supervisor MUST NOT rename, organize, archive or delete a chat, MUST NOT delete a library bundle, MUST NOT discover or generate a title and MUST NOT translate — those are exactly the jobs that would otherwise take a slot away from a live request. An explicit operator pin overrides the partition, because the pin already names one canonical agent and refusing it by role as well would leave the task reachable by no pool at all; agent ids are canonical in both the `worker-N` and `supervisor-N` namespaces. `TRANSLATE_MARKDOWN` keeps the Supervisor's shape on the Worker side — the Worker stays with the task until its translation artifact is delivered — but releases the conversation as soon as that artifact downloads.
- A non-empty browser-agent semantic `dedupe_key` MUST identify at most one active task across every task type, including `BOT_WRITE` and `RECOVERY_WRITE`. Restoring the renderer may request the same write repeatedly; those requests converge on the oldest active durable task and MUST NOT create additional provider submissions. A terminal task does not suppress a later explicit retry with the same key.
- The Agent labels its automated, request-bound ChatGPT surface **Engine**. A separate project-scoped **ChatGPT** surface MAY provide direct human browsing/conversation, but it MUST register no Wharness prompt, activity, bundle, recovery, affinity, or account-automation listeners; it exposes only ordinary browser navigation and remains subject to the same renderer isolation and overlay suspension rules.
- Desktop multi-window project ownership MUST be explicit: one canonical project path may belong to only one live Wharness window at a time. A window MAY bind several projects and project switching MUST preserve each bound local renderer state. The ChatGPT Supervisor/worker pool is global to the authenticated Desktop process, not multiplied per window or project; the Supervisor is attached to the active owning window and workers remain hidden except while one Worker is explicitly surfaced by the trusted local Agent runtime interaction control.
- The privileged Wharness preload MUST be attached only to the trusted local frontend origin and MUST expose narrow, named IPC capabilities rather than `ipcRenderer` or generic send/invoke primitives.
- Wharnex MUST NOT inspect ChatGPT cookies, local storage, generated response prose, or authentication state during normal ChatGPT transport/account automation. The non-executing `TRANSLATE_MARKDOWN` utility worker is a narrow artifact-only exception to the response-output boundary: it MAY upload one bounded request bundle, request one exact `whx_translation_res_<task_id>.zip` result, activate only that file/download affordance, and hand the bounded bytes to the translation engine as utility data; it MUST NOT read assistant prose, and those bytes MUST never be treated as executable instructions. Permitted DOM interaction is limited to the named transport and Wharnex-owned account-management operations above; it MUST NOT infer model content/completion from response text. Electron persists the remote browser partition and MAY export/import that partition only as an opaque user-requested Wharnex session backup that is treated as a secret. ChatGPT authentication has two explicit user-selectable modes: **Embedded**, where compatible login navigation remains inside the sandboxed ChatGPT `WebContentsView`; and **External browser**, where Wharnex launches a real Chrome/Chromium/Brave process with a Wharnex-owned persistent dedicated profile and loopback-only DevTools endpoint, always starting again at `https://chatgpt.com/auth/login`. An in-flight OAuth URL created in Electron MUST NEVER be handed to another browser. The sole credential-inspection exception is the external-auth callback relay: after the managed browser proves an authenticated return to `chatgpt.com`, main-process code MAY read only `chatgpt.com` cookies from that Wharnex-owned dedicated profile and write them directly to the dedicated Electron cookie store. Cookie values MUST never enter the renderer, logs, project context, or generic IPC; unrelated-domain and Cloudflare/anti-bot cookies MUST be excluded, and the dedicated browser profile MUST remain private under Wharnex `userData`, persist across successful/cancelled login attempts, and be deleted only by an explicit browser-session/full-data clear.
- A dev-only ChatGPT behavior probe (`adr/ADR-0041`) MAY measure account-automation controls for diagnosis. It MUST name its control from a closed enum, MUST build every script from constants so no caller string reaches the page, MUST re-bound its result before it crosses IPC, and MUST stay inert unless explicitly enabled. It MUST NOT click, navigate, mutate the account, read assistant prose or conversation content, or be reachable from a model plan.
- The desktop context-copy IPC MUST derive the backend bundle URL internally from an allowlisted local backend plus a validated session ID. Renderer-supplied arbitrary fetch URLs are forbidden.
- ChatGPT remote permissions are denied unless explicitly allowlisted in the security model.
- Native clipboard file references MUST point only to context artifacts generated by Wharness in its temporary context directory.
- Automatic ChatGPT input transport MUST NOT switch the visible Inspector tab or explicitly focus the remote WebContents. Native mouse/key events may target the ChatGPT WebContents while the Wharness window is already focused; explicit focus is reserved for user-invoked bridge actions.
- The visible Supervisor keeps background throttling disabled while visible or inside an explicit navigation/write critical phase. Worker automation is driven only by the durable scheduler and performs bounded non-preemptive jobs. Each physical Worker slot MUST remain resident on its current conversation for a 60-second default dwell, never configured below 30 seconds; free slots MUST serve unresident lanes before resident slots rotate. Residency is an affinity cache and MUST NOT become ownership: a resident lane that yields no claimable work for a bounded idle window after its dwell MUST be released so the slot rejoins the free pool, and a slot that is blocked from claiming MUST NOT reserve its lane against the rest of the pool, because a lane no slot can serve is a conversation the queue cannot reach at all. Cross-chat navigation starts MUST be separated process-wide by a gate derived from the provider's own durable 429 evidence: a healthy provider uses a short floor, and each rate-limit level widens the gate up to the protective 30-second ceiling. A fixed ceiling applied while the provider is healthy is not protection — it serializes the whole pool behind one clock while conversations hold due work. Residency/rotation state is ephemeral Desktop state, while request eligibility, valid processing-duration samples, and provider 429 cooldown state are durable backend state. `AWAIT_RESPONSE` MUST be a passive resident probe that releases the worker through `WAITING`/`not_before` at a healthy 30-second observation cadence and MUST NOT focus the composer, reload, or navigate a healthy conversation. A conversation that is producing a response MUST be quiet: while its `AWAIT_RESPONSE` is still claimable, no task that drives that conversation's own surface (`ORGANIZE_CHAT`, `RENAME_CHAT`, `ARCHIVE_CHAT`, `DELETE_CHAT`, `TITLE_DISCOVER`, `TITLE_GENERATE_TEMP`) may be claimed for it, and that rule MUST be enforced by the durable claim rather than by a client-side check, because supervision spends almost all of its life in `WAITING` and the lease lock therefore leaves a window open on every observation cycle. Each of those tasks navigates or mutates the generating renderer — a project move is a real navigation, archive/delete click ChatGPT's own Stop control, and the temporary-title fallback sends the worker to a new chat — so running one mid-generation destroys the response. A supervision past its attempt budget MUST be excluded, or a dead await silences its conversation permanently. The resident slot MUST keep its lane while it is between observations. A terminal "finished without delivering" conclusion MUST rest on evidence the turn actually ran: when the generating indicator was never observed for that request, a substantially longer settle window is required, and supervision scheduled immediately after a write MUST wait the same initial delay as a first request so its first probe cannot read the preceding turn. A passive observation of a provably still-generating page is not an attempt and MUST NOT consume the task's bounded attempt budget; supervision ends on evidence of trouble, never because a healthy response outlived a retry counter. The same applies to every probe outcome in which nothing was attempted at all — a slot that was not on the expected conversation, an active provider cooldown, a worker slot rebound before the task started, or a page in neither a generating nor a completed state: charging the attempt budget for work that never reached ChatGPT retires healthy supervisions as exhausted. Because the attempt budget is the only defence left once an outcome is charged, `last_error` MUST record what consumed an attempt: a passive observation MUST NOT overwrite the error of a real, attempt-consuming failure, or a task reads as merely waiting while the failures draining its budget are erased one by one. Because such outcomes are free, the ambiguous case MUST carry its own evidence-shaped bound: a page showing no structural sign of life at all for a bounded stall window moves to `ATTENTION`, and any generating, completion or download signal resets that window. A structural completion is a single instant of a live page and MUST be confirmed — still complete, bundle still absent, after a grace window measured from the moment the generating indicator disappeared — before it may conclude that the response finished without delivering. Delivery continuations are themselves provider requests: they MUST be spaced and remain bounded by `MAX_BUNDLE_CONTINUATIONS`. Autonomous prompt submissions MUST additionally be separated process-wide, because transport serialization is per worker slot and would otherwise let every free slot submit simultaneously against one authenticated account. Each task assignment MUST advance the worker rotation, whether or not the slot had to rebind, so a slot serving its own resident lane cannot hold the head of the rotation indefinitely. A trusted local user MAY explicitly surface one idle Worker `WebContentsView` for direct interaction or **Seguir (flow)** in the main Engine area; a running Worker keeps its stable automation viewport and exposes bounded screenshots for observation instead. Surfacing MUST NOT transfer scheduler ownership, create arbitrary navigation IPC, expose cookies/storage/DOM through IPC, or keep the Worker visible after the interaction surface closes, the frontend renderer dies, or its owning window closes. Supervision MUST NOT depend on remote-page timers. A structurally detected anti-bot/auth/access/provider-wide gate or exhausted bounded recovery MUST pause the provider once and publish explicit human attention instead of producing concurrent retry storms; ChatGPT rate limiting MUST be assumed only when ChatGPT's own limit control is structurally present in the page DOM; that control MUST suspend the Workers durably for the configured window. An HTTP 429 from any endpoint, including repeated ones, MUST NOT suspend Workers or count as rate-limit evidence: every open ChatGPT page makes its own background calls and ChatGPT refuses some of them (the sidebar conversation list above all) while the account keeps submitting normally. An HTTP 429 is recorded as a diagnostic only. While a suspension is active, workers MUST stop claiming rather than claim and immediately return to `WAITING`: a claim charges an attempt, so claiming through a cooldown spends the queue's own bounded retry budget on a provider that is refusing every caller. A suspension MUST NOT consume task attempts, MUST NOT be shortened by a lesser rate-limit observation that arrives while it is still counting down, and MUST resume in stages — the gate pins the rate-limit level at its ceiling so cross-chat navigation and autonomous submission spacing both resume at their protective width and decay back to the healthy floor only as valid bundles prove the account healthy. Detection MUST remain structural and language-neutral and MUST NOT read localized status prose. A rate-limit gate is not a human-action kind: it clears on its own and MUST NOT raise a human-attention notification.
- Rate-limit suspension scope amendment: automatic HTTP 429 and structural account-limit evidence MUST durably suspend only ordinary Worker claims and Worker provider actions. Supervisors and the ephemeral Translator MUST continue claiming and operating; their observations still record rate-limit evidence so the Worker suspension can be widened or restarted. This rule replaces any broader “whole provider”, “both pools”, “every caller”, or “all automation” suspension wording earlier in this section. Worker suspension MUST remain attempt-free, MUST NOT be shortened by lesser evidence, and MUST still require the bounded Worker reload/health probe before ordinary Worker claims resume. Manual Worker suspension MAY cover every ordinary Worker task type or a validated selected set, MUST be enforced by the durable claim predicate before an attempt is charged, and MUST NOT affect Supervisors or Translator. Account-maintenance and title task types are selectively suspended by default until the operator explicitly changes that policy.
- `Retomar pedido` MUST NOT treat durable task state, upload completion, an armed expectation, spinner/progress controls, assistant-count changes, or a previously observed POST as proof that the original request reached the bound ChatGPT conversation. Before sending a short same-request `keep continue` request, the owning Supervisor MUST prove structurally that an already-submitted user turn in that conversation contains an attachment/resource card whose engine-owned filename exactly matches the canonical Wharnex request archive for the pending request. This proof MUST NOT read user prompt prose or assistant prose. If the proof is absent, resume MUST retire stale response supervision and use the idempotent full-archive resend path backed by the persisted request artifact; it MUST NOT arm `AWAIT_RESPONSE` or send the short continuation.
- While the user-selected **External browser** authentication flow is active, the affected embedded remote view stays hidden. The managed browser must be a real Chrome/Chromium/Brave executable, use a Wharness-owned persistent dedicated profile, bind DevTools only to `127.0.0.1`, and begin from `https://chatgpt.com/auth/login`. Return to non-auth `chatgpt.com` plus a successful in-browser auth-session check is the callback signal. Wharness then performs the narrow ChatGPT-cookie relay described above, closes the managed browser, preserves its dedicated profile for future Google/ChatGPT sign-in reuse, and reloads the embedded view. The ordinary personal Chrome profile MAY be opened only as a manual isolated shortcut and MUST NOT be inspected, debugged, or presented as callback-capable. Google OAuth MUST be handed to this managed-browser flow when selected from Embedded mode because Google disallows embedded user-agents. The ordinary operating-system browser remains a manual, session-isolated fallback and MUST NOT be presented as callback-capable.
- While one manual request is pending, the Desktop MAY normalize a generic downloaded ZIP filename to the exact canonical `wharness-bundle-<request_id>.zip` bound to that active chat. It MUST NOT rewrite a different valid Wharness request id.
- Durable Harness chat attachments MUST live in Wharness-owned application storage, never inside the target project, and renderer IPC MUST address them through validated opaque references rather than arbitrary paths.
- Leaving the ChatGPT tab or Agent mode MUST hide the native remote view so it cannot intercept interaction over other Wharness surfaces. Ordinary application dialogs are non-blocking internal windows and MUST NOT suspend the native remote view merely because they are open. Only an explicitly trusted blocking overlay marked for ChatGPT suspension may hide the remote view until that blocker closes.
- Archived chats open in a temporary read-only preview without creating an active tab or resuming orchestration. Sending, response processing, and remote automation remain disabled until explicit restore.

## 9. Local lifecycle invariants (v1.2.1)

- Repository-root `make build`, `make start`, `make stop`, `make status`, and `make logs` are the canonical local lifecycle commands.
- Build commands MUST resolve Docker/build paths from the repository root, not from the caller's current service directory.
- `make build` MUST materialize the configured local Protected runner image as part of a complete machine build, so a fresh checkout cannot fall through to Docker registry authentication for a missing local-only image. Transactional self-evolution MUST continue to use `make build-stage`, which MUST NOT rebuild the runner image.
- Normal rebuilds MUST avoid unconditional package-manager hydration: dependency cache invalidation is keyed by lock/dependency metadata and runtime versions, while explicit refresh remains available for recovery.
- A `node_modules` tree is shared by two runtimes, the operator's host (glibc) and the self-evolution build container (musl), so it MUST remain loadable by both. Dependency sync MUST complete it with the other libc's native packages pinned in the lockfile, verified against the lock's integrity (`scripts/hydrate-native-variants.mjs`). A variant that cannot be fetched is reported and MUST NOT fail the current runtime's build.
- Successful backend/frontend/desktop build artifacts MAY be reused only through content/runtime fingerprints; a missing expected artifact or changed component input MUST invalidate that component, and an explicit forced rebuild path MUST remain available.
- The development launcher MUST show a short splash before Desktop startup and compare the current source fingerprint with the last successful build fingerprint. A changed or absent fingerprint MUST stop the owned Desktop, complete `make build`, and only then start the Desktop; a failed build MUST NOT advance that fingerprint.
- The installed/OS launcher and `make start` MUST enter the same checkout-owned lifecycle, instance id, Compose project, host ports and persistent Electron profile. Before either invokes Electron — including the launcher splash — it MUST remove inherited Electron-as-Node mode so a desktop shortcut cannot silently execute the Electron entry point as ordinary Node while `make start` succeeds.
- The frontend production build MUST ship Monaco from its versioned precompiled local distribution instead of rebundling Monaco's source module graph during every Wharness rebuild.
- `make start` MUST track only processes it owns under `.harness/run`; `make stop` MUST NOT indiscriminately kill unrelated processes already using the same ports.
- Starting the host terminal daemon MUST self-heal. A pid file naming no live process is discarded. A live daemon that still runs the terminal binary but does not answer on its socket is retired after a short grace period, because deleting only its files lets it outlive the restart and remove the new daemon's socket. A daemon that dies during startup MUST fail fast, be retried once, and on final failure print the tail of its log. A pid that no longer runs the terminal binary MUST never be signalled.
- Linux Electron startup MUST support an explicit `WHARNESS_OZONE_PLATFORM=x11|wayland` override and default safely when both Wayland and XWayland are present.
- Runtime PID/log files belong under `.harness/` and MUST remain excluded from project context and source control.
- The Compose project identity for a checkout MUST come from `WHARNESS_COMPOSE_PROJECT_NAME` when set, and otherwise default to that checkout's own folder name (never an opaque hash of the absolute path). The canonical Compose application stack MUST publish only the gateway, defaulting to loopback port 6969 and overridable per checkout via `WHARNESS_GATEWAY_PORT`; backend, local frontend and paired remote webapp remain private to the Compose network. Bare local development MAY continue to use the historical direct 8888/5173 backend/frontend ports outside stack mode. A checkout MAY persist its stack overrides in its own gitignored `.harness/env` (a plain `KEY=value` file sourced by `scripts/stack.sh`/`scripts/start.sh`/`scripts/status.sh`/`scripts/database.sh`) instead of exporting them in every shell session.

## Storage reclamation invariant (v1.2.103)

- Every lifecycle command that builds or installs — `make build` and therefore `make build-all`, `make build-refresh`, `make install-dev`, and the `make start` path that rebuilds a stale checkout — MUST reclaim obsolete storage as part of that command, not as a separate chore an operator has to remember. Reclamation runs after the replacement services are healthy, so the generation being retired is never the one the rollout still depends on.
- Reclamation is **obsolescence-proven, never unconditional**. It MUST NOT remove a valid fingerprinted dependency or compiled-artifact cache, a live sandbox workspace, a persisted session, request history, a current context base, or an artifact. Wiping a valid cache to reclaim disk trades storage for a full rehydration and recompilation on the next build, which increases total consumption rather than reducing it, and it contradicts the fingerprint-reuse rules above. `make clean`, `make deps-refresh` and `make build-refresh` remain the explicit unconditional paths.
- Ownership is split by what each side can prove. The backend owns what it has records for — temporary directories it created, sandbox workspaces, and per-project dependency caches no session reaches — and reclaims them through its own ownership-aware endpoint. The host owns what the backend cannot see: settled self-evolution transaction directories, unbounded lifecycle logs, and the Docker layers and build cache every rebuild orphans. Neither side may sweep by name alone across a root it does not own; the backend's temporary sweep stays confined to the checkout-private temporary root.
- Every temporary directory Wharnex creates MUST be reclaimable by the sweep. A prefix that has an owner responsible for removing it on the normal path is still a leak when that path does not run, so the sweep's prefix set MUST cover all of them and MUST be kept in step when a new one is introduced.
- A settled self-evolution transaction directory is retained by age and count, not forever. The transaction the self-evolution status still names, and the most recent few whatever their age, MUST be kept; the exclusive-resource recovery invariant's requirement that a release leave its directory on disk as evidence binds the release operation, and is satisfied by that retention window rather than by unbounded accumulation.
- Reclaiming Docker layers MUST NOT be able to remove the image-level rollback path application activation depends on. Only untagged layers and build cache unused for the whole retention window are eligible, so the immediately previous generation is never the thing reclaimed. Anonymous Docker volumes are machine-global and MAY hold a third-party image's data, so reclaiming them is opt-in and MUST be restricted to volumes Docker itself reports as attached to no container; a named volume — this checkout's PostgreSQL and MinIO state above all — MUST be out of reach by construction.
- Host-side reclamation is housekeeping and MUST NOT fail the lifecycle command that invoked it. What it could not reclaim, and what remains reclaimable only behind an explicit opt-in, MUST be reported instead.


## Git workspace invariant

- Every opened project root must own a Git repository. The backend may run `git init` automatically when `.git` is absent.
- Do not auto-commit or rewrite host history during Git bootstrap.
- When the host has an existing Git repository, sandbox copies are a real local clone of it (`git clone --local`), sharing its actual commit history; a host with no repository yet gets a fresh synthetic Git baseline instead. Either way the host's own `.git` directory is never copied byte-for-byte into a model execution workspace.
- Opening/restoring a project MUST initialize the Agent workspace in Protected + Auto. A user may switch that open project to Unprotected or Full only through explicit confirmation; either host-direct mode disables Auto. Every Unprotected plan execution requires another explicit confirmation; Full acts as a standing waiver only for Policy approval items explicitly marked `bypass_in_full`, while sudo remains one-shot approval/password gated.
- The interactive Editor terminal is a human-only Host PTY and is independent of Agent Protected/Unprotected/Full mode. Normal UI MUST NOT expose the legacy Sandbox terminal target; Protected Agent execution still uses its isolated copied workspace.
- Patch fallback may use `git apply --recount` or checked `--3way` only after a dry/check pass; never partially apply a failed fallback. Surface Git stderr on failure.
- Restored/legacy sessions MUST self-heal a missing `whaness.yml` through the validated default config creator before project settings are returned; a missing config file must not strand the UI in an indefinite loading state.

## Chat conversation affinity invariant (v1.2.6)

- A workspace MAY contain multiple Harness chats; each chat MUST own an independent Harness session identity and local transcript.
- Each Harness chat MAY bind to exactly one stable ChatGPT conversation URL. Once a concrete binding is established it is immutable for the lifetime of that Harness chat: generic saves, remote-state updates, navigation, explicit sends, conflict resolution and recovery MUST preserve it. The binding is durable metadata and MUST survive frontend/Desktop restart.
- Switching Harness chats MUST navigate the remote ChatGPT surface to the URL linked to the selected chat when one exists.
- An unbound Harness chat MUST begin from the ChatGPT new-chat/home surface and MAY auto-bind only after a concrete trusted `chatgpt.com/.../c/...` URL exists.
- After a new-chat submission, Desktop MUST wait until the concrete trusted `/c/...` URL is stable and no longer loading before publishing it as the definitive affinity candidate. ChatGPT's transient `/c/WEB:...` creation URLs are not definitive and MUST NOT be persisted. Candidate persistence/confirmation MUST be owned by application-level state, not by whether the ChatGPT inspector pane happens to be mounted; missed candidate events MUST be reconciled from per-chat Desktop state. Switching away from or back to a submitted unbound chat MUST preserve its owned renderer and pending affinity instead of navigating it back to the home surface.
- A chat's archive state is durable state and MUST reach the chat row, not only the browser and the session (see `adr/ADR-0048`). It MUST NOT be cleared by omission either, for the same reason as the conversation binding; archiving and restoring are explicit actions, and archiving an already-archived chat MUST NOT move its archive timestamp.
- A conversation binding MUST NOT be cleared or replaced (see `adr/ADR-0047`). A generic chat save is a full replace of a renderer-owned row and the renderer omits the field whenever its own copy has none, so omission decoded as empty is indistinguishable from a deliberate clear — which silently unbound chats on ordinary title and transcript saves. A save or remote-state update MAY establish the first binding only; every later empty or different value MUST preserve the established URL and conversation id. This MUST be enforced in the durable store, not in one renderer path.
- A legacy chat that has no binding MUST have a way back that does not depend on the operator remembering the conversation. Wharnex MUST be able to propose candidates reconstructed from records it already holds — its own browser-agent queue for that chat, the chat's transcript, the session's event history — naming which evidence produced each one, and MUST mark a conversation already owned by another chat as a conflict rather than offering it. Recovery MAY establish only the missing first binding; it MUST NOT replace an existing one.
- Once a chat already has a ChatGPT URL, navigation and explicit Harness Send MUST NOT replace it. A mismatched visible conversation is restored to the immutable linked conversation before any request-bound transport proceeds.
- Conflict resolution MUST continue in that same immutable linked ChatGPT conversation. It MUST NOT create an auxiliary provider conversation, synthetic `_cf_` ownership key, or a second response supervisor for the request.
- Deleting a Harness chat MUST retire that chat's remaining browser-agent queue in the same operation. Every task that operates on the conversation — response supervision, title discovery, organization, rename, archive — becomes work for a chat that will not exist, and leaving it claimable pins workers to abandoned conversations and holds the single global account lock against live chats. The remote cleanup jobs are the deliberate exception: deleting the conversation, its temporary sibling and its library bundles is what deletion still has to accomplish. Convergence MUST be owned by the queue itself, so that every deletion path reaches the same state.
- Desktop navigation IPC MUST accept only trusted HTTPS `chatgpt.com` origins. Never expose arbitrary renderer-controlled navigation.
- While an expected Wharness bundle is active, liveness recovery MAY use only bounded transport/renderer failures and narrow structural activity signals already allowed by the ChatGPT transport. Recoverable connection failures reload the owned renderer; silent/stalled or ambiguous processing MUST request human attention and MUST NOT inject an automatic same-request recovery prompt. Recovery MUST NOT inspect assistant prose for decisions, change task scope, cross chat ownership, or loop indefinitely.
## Concurrent host integration invariant — Git-native (v1.3, superseding the ChangeSet/CAS mechanism)

- A project fingerprint is provenance, not a global mutation lock. Peer or external edits MUST NOT automatically supersede an in-flight planner request.
- This is the primary integration and communication protocol between the sandbox and the host. A verified sandbox candidate MUST be committed onto its own dedicated branch (`whx/<request_id>`) inside the same Git clone the sandbox already is, using a fixed non-human author identity and the plan's own `commit_message` (a mandatory field for `change` plans) plus `Request-Id`/`Plan-Id` trailers, never the operator's own configured Git identity or an unsanitized planner string. That `commit_message` MUST be meaningful developer-facing history derived from the actual patch: accurate Conventional Commits type (`feat` for new behavior, `fix` for a bug/corrective patch, etc.), useful scope when clear, and a concrete implemented/corrected outcome; generic bookkeeping subjects such as `update files`, `apply patch`, `requested changes`, or `Wharness-verified change` are not acceptable protocol output. That contract MUST be enforced, not merely published: a `change` bundle whose `commit_message` is missing, is not Conventional Commits, exceeds the 72-character subject limit, or matches the forbidden bookkeeping set MUST be rejected at ingestion — before Policy and sandbox verification, so a rejected message never discards a verified candidate. `commit_message` is a full Git message: subject, one blank line, optional body explaining why. Wharness MUST preserve that body verbatim and MUST NOT flatten it into the subject.
- That branch MUST be pushed only locally (an absolute host filesystem path, never a network remote, never the operator's own configured `origin`) into the host's own `.git`. Apply MUST integrate it as a real two-parent merge commit (host, candidate) — the history `git merge --no-ff --no-edit` would produce — into whatever the host currently has checked out, then rerun the plan's own verification commands against the merged result.
- A failed post-merge verification MUST revert the host with `git reset --hard` to its exact pre-merge commit before entering the repair loop. If Wharnex first preserved dirty operator work in a snapshot commit, that snapshot commit — not the older HEAD observed before preservation — is the exact pre-merge rollback boundary, so the operator's work survives failure. An Apply batch MUST be all-or-nothing before it starts: the whole batch is simulated in order, each candidate merged three-way from its own request base onto the result of the ones before it, and a candidate that would stop the batch is reported before any candidate reaches the host (`adr/ADR-0077`). A revert of merges already made MUST wait out transient index-lock contention (an editor polling `git status`), MUST verify that HEAD reached the pre-merge commit, and MUST publish its failure; it MUST NOT be discarded. A Protected session with automatic approval that is parked in `failed` holding verified candidates MUST be resumed by the Engine itself once the live host is proven to accept the whole batch, because its approval already covers that integration. It requires no round in flight, no pending manual request, and no live conflict record. Recovery MUST run at startup and periodically, MUST attempt each (session, host HEAD, candidates) state at most once, MUST NOT start a planner round when the retried Apply fails, and MUST publish `integration.auto_recovery_*` events. A manual-approval session is never resumed automatically. A planner-resolvable merge conflict MUST abort before it touches the host working tree and creates one bounded `harness.conflict/v1` support request limited to the conflicting paths, sourced via `git show` against the conflict's merge-base/host/branch commits — never a generic repair attempt. `.wharnex/knowledge/**` is Wharnex-owned integration state, transported separately and never planner-patchable: a conflict confined to that subtree MUST be resolved locally by preserving the current host version, and a mixed conflict MUST omit those managed paths from the capsule while retaining the ordinary conflicting paths. The integration branch is deleted only after a successful merge and verification, or when its candidate is deliberately disposed of — an operator rejection, or archiving the chat that owns it (see `adr/ADR-0031`), both of which clear the candidate record in the same step so no Apply that can only fail is ever offered. A branch MUST NOT be released while its candidate is still pending on a live session, including a failed one still open for repair. The merge commit itself remains in the host's log regardless.
- Only the short host merge+verification phase is serialized per canonical project. This internal Git plumbing is Wharness's own execution engine mutating the host it already owns — analogous to Apply writing files without per-file approval — and is a distinct authority from a model-requested `git` command inside a plan's own operations, which still requires explicit user approval per the Git workspace invariant's mutation rule.

## Request-base-rooted integration invariant (v1.3.2, completing ADR-0029 — see `adr/ADR-0035`)

- Every planner request MUST record the exact planner-visible host tree its context was snapshotted from, as a real commit parented on the host's HEAD and anchored under `refs/wharnex/base/<request_id>`. Capture MUST NOT disturb the host's index, HEAD, current branch or working tree, MUST stage through a private temporary index, and MUST honour the project's own `.gitignore`. Because project knowledge is transported separately and cannot be planner-patched, dirty working-tree state under `.wharnex/knowledge/**` MUST NOT be staged into the request-base commit; that subtree retains its parent HEAD version so volatile managed materialization cannot become candidate-owned ancestry. The anchor lives outside `refs/heads`/`refs/tags` so ordinary Git UX is unchanged. Capture and rooting are best effort: a repository with no commit, or any Git refusal, MUST degrade to the previous behavior rather than fail the user's request.
- A verified Protected candidate's integration branch MUST be rooted at its own request base, and the plan's patch applied to that tree — never to whatever the host has advanced to since the request was planned. Applying a patch to a tree it was not authored against is a dead end that no retry and no source patch can resolve, and it MUST NOT consume an automatic AI repair round.
- Rooting a request at its immutable base changes which tree executes, never which project owns the run (see `adr/ADR-0045`). The extracted base is a temporary directory; every project-scoped resource — the private dependency cache above all — MUST stay keyed on the canonical project, and preparation MUST be told that project rather than left to infer it from the tree it is handed. Correcting the identity after preparation is not sufficient and MUST NOT be relied on: resources derived during preparation are already bound by then.
- Archive completeness MUST be measured against what a patch modifies, reads and declares as a barrier — never against what it creates. A created path cannot exist in a snapshot taken before it existed, so requiring it makes reconciliation impossible for every change that adds a file and forces the fallthrough this SoT already forbids. Created paths MUST also be withheld from base hydration, so the base stays faithful to the tree the patch was authored against and a peer's colliding creation is decided by the real three-way merge rather than by a patch error.
- A `change` bundle MUST be able to deliver what it declares: an `impact_files` entry that the patch does not write **and** that does not exist in the project promises a file that will exist nowhere, and MUST be rejected at ingestion before Policy and sandbox verification. Both conditions are required and the check MUST fail open — a path it cannot resolve counts as deliverable — because rejecting a legitimate change is worse than missing a detection. This obligation runs in one direction only; it does not make `impact_files` authoritative for anything else.
- Whether two changes can be combined is decided by a real three-way merge, never by impact-file, line-range or column overlap. `impact_files` remains a scheduling forecast only. A dry-run merge (`git merge-tree`) MAY be used as an advisory preflight so a merge already known to be doomed never mutates the host; it MUST compare against the host's real current content including uncommitted state, MUST treat an unsupported Git as "unknown" rather than "clean", and MUST NOT replace the atomic merge as the authority. That merge, its preflight and every conflict capsule MUST be three-way from the candidate's **own request base** — the nearest Wharnex request-base commit on its first-parent chain — never from the common ancestor Git computes (see `adr/ADR-0077`). A request base is HEAD plus the operator's uncommitted work, and the host never descends from it, so Git's computed base is the bare HEAD: every piece of operator work that predates the request then counts as a candidate change, producing conflicts on files nothing diverged on and silently restoring operator edits that were discarded after the request was taken. A dirty checkout — the operator, or another agent, editing the project while a request is in flight — MUST NOT by itself produce a conflict; only the same lines changed on both sides may. A caller-supplied request-base ref counts only when it is provably an ancestor of the candidate, and only a candidate that carries no request base falls back to Git's own merge-base.
- A `harness.conflict/v1` capsule MUST carry the intent of both colliding sides — the candidate's own planner-authored purpose, and the purpose of the already-integrated changes it collides with, taken from the commit messages the protocol already requires — plus the attempt number, its bound, and what earlier rounds of the same conflict already tried. Conflict resolution remains bounded; the history informs that bound rather than extending it.
- A `harness.conflict/v1` capsule MUST travel as the fixed `conflict/capsule.json` entry of the logical request ZIP and MUST NOT be inlined into the bounded planner prompt. Conflict resolution supersedes only its named paths: every non-conflicting file from the owning verified candidate remains in the cumulative sandbox and Apply candidate, including when that predecessor is Git-native and has no legacy `ChangeSet`. While a durable integration conflict exists, transient state/request flags MUST NOT permit Apply of the stale predecessor. A conflict record the live host no longer reproduces MUST be released rather than left blocking Apply. Release requires proof: every pending candidate is shown, by the request-base merge of `adr/ADR-0077`, to integrate with no planner-resolvable conflict (a branchless, patch-only candidate by its patches applying to the host as it stands; a legacy `ChangeSet` candidate is never proven); the record holds no manual resolution; and no round is in progress. It MUST NOT retire any candidate mutation, because the candidates were just proven to integrate whole. A preflight that cannot answer keeps the record. Releasing an **orphaned** record, one whose round can no longer arrive, MUST NOT retire any candidate mutation either. No round will ever deliver a replacement for its paths, so retiring them discards the candidate's own verified work; the next Apply measures those paths again, and a collision that still exists becomes a fresh capsule. Only rounds a later resolution of the same lineage already replaced may retire paths. A failed focused round continues from the same immutable capsule with its new local failure evidence; it MUST NOT be rebuilt from an empty or inapplicable conflict representation.
- A compare-and-swap integration race that persists across every restage attempt MUST be escalated to the bounded focused-resolution path, scoped to the racing paths, and MUST NOT be reported as an indefinitely retryable condition: replaying the same candidate against the same host reproduces it forever. An unattributable race keeps its previous classification rather than becoming a conflict with nothing to resolve against.
- Per-project execution concurrency is an operator setting that defaults to one and MAY be changed at runtime. A UI/API change MUST persist as Wharnex operational state and survive backend/Desktop restart; the environment value is only the fallback before an operator value exists. Lowering it MUST NOT interrupt work already running; the project admits nothing new until it drains under the new limit. Raising it MUST admit plans already waiting, not only later submissions. The ceiling MUST stay small because each concurrent runner claims a full container memory allowance and a complete project clone.
- A candidate reconciled from an immutable archived request base (no Git ancestry shared with the live host — see `SoT/SANDBOX_MODEL.md`) has nothing to branch or merge onto and MUST keep using the legacy canonical base/result `ChangeSet` materialized and integrated via per-file compare-and-swap and conditional rollback instead.
- Clean disjoint changes require no model turn. A true conflict, from either path, preserves unrelated verified mutations.
- Replaying an earlier pending candidate into a verification sandbox that shares no Git ancestry with the host (one rebuilt from an immutable archived request base) MUST NOT attempt a branch merge: git refuses unrelated histories, which is neither a conflict nor recoverable. Such a candidate is fetched into the workspace and merged three-way from its own request base (or its parent) onto the workspace's current tree; if the host no longer holds that commit, it is replayed as the plan's recorded patches. A collision there is a `harness.conflict/v1` conflict like any other and MUST NOT reach the generic repair loop, whose planner cannot patch a replay that runs before its own plan. The raw commit diff remains only for a Git build that cannot merge from an explicit base.
- The only host-facing mutation in the verification phase is pushing the verified integration branch into the host's `.git`, and that alone is serialized per project. Per-project execution concurrency is an operator setting that defaults to one; raising it MUST NOT be treated as free, because each concurrent runner claims a full container memory allowance and a complete project clone.

## Host repository shape invariant (v1.3.4 — see `adr/ADR-0039`)

- The host project's repository shape is a **measurement, never an assumption**. Wharnex MUST resolve a repository's real Git directory before writing into it (`.git` is a file, not a directory, in a linked worktree and in a project root that is itself a submodule), and MUST derive its submodule inventory from the index rather than from `.gitmodules`.
- A host worktree's uncommitted state MUST be classified by what Git can actually capture, not by whether `git status` is non-empty. Dirty submodule content and untracked embedded repositories are reported as modified but are not capturable by a superproject commit; treating them as capturable is what made a dirty submodule block every host integration permanently.
- Preserving the operator's uncommitted work before an integration MUST succeed when there is nothing a superproject commit can hold. That is a normal outcome, not a failure.
- `git add -A` MUST NOT be allowed to record an untracked embedded repository as a gitlink in any Wharnex-authored commit (the pre-merge snapshot, the request base, the project baseline). Such a commit claims to preserve the operator's files while holding only an unresolvable pointer, so the revert built on it cannot restore them. Embedded repositories are excluded by pathspec and reported as left in place.
- Wharnex MUST refuse, not proceed, when the host holds unresolved paths or an in-progress merge/rebase/cherry-pick/am, when its repository index is locked by another Git process or by a crashed one's leftover `index.lock`, and when an integration would move the recorded commit of a submodule holding uncommitted work. A locked index MUST be classified, not returned as a generic Git failure: it is indistinguishable from a source defect to every layer above, and no planner patch can remove a lock file, so the generic path spends an automatic repair round on a question the planner cannot be asked and the next Apply reproduces it exactly. Wharnex MUST NOT delete the lock itself — removing one a live process still holds corrupts that process's write — and MUST instead report the lock's path and age, because age is what tells the operator whether to wait or to delete. Refusal MUST be a typed condition carrying the reason, the paths and the operator action that clears it, classified `host_working_state_blocked`: the verified candidate is retained and no automatic repair round is consumed.
- Commits and merges Wharnex makes on a host repository are its own internal bookkeeping. They MUST use the fixed non-human identity, MUST disable signing, and MUST disable project hooks — a project's own `pre-commit` gate has no authority over Wharnex plumbing and MUST NOT be able to block host integration.
- A merge or revert that moves a submodule's recorded commit MUST realign that submodule's checkout, which Git deliberately does not do. Realignment MUST be offline (never fetch) and MUST NOT touch a submodule holding uncommitted work; every skip MUST be reported, because the superproject is then knowingly ahead of a checkout the operator must update.
- A `change` bundle whose patch writes inside an initialized registered submodule MUST be represented as a repository-tree candidate: Protected verification preserves independent Git metadata, commits run deepest-first, and the superproject candidate records the resulting gitlinks plus each submodule's checked-out branch and base commit. Apply merges the superproject candidate and MUST ensure the recorded nested commit is contained by the checked-out branch, fast-forwarding to that exact commit when it is not already integrated and never detaching or rewinding the branch; rollback MUST restore the root gitlinks and the branch positions Apply actually advanced. An authoritative conflict on an exact owned gitlink MUST be reconciled locally to the descendant of the validated base and candidate; no ordinary path may inherit that exception. Temporary nested integration branches MUST be removed after success when the original branch retains the commit. Dirty, uninitialized or missing nested repositories remain typed fail-closed conditions; no remote push is implied. Persisted repository candidates are durable protocol state: migrations MUST preserve nested-repository ownership (including legacy `integration_units`) and MUST NOT silently degrade a repository-tree candidate into a root-only merge; any recovered checkout identity MUST be proven compatible before Apply, including an idempotent already-integrated commit without ever rewinding the operator branch. A project Wharnex cannot inspect MUST be admitted unchanged: a measurement failure MUST NEVER reject a legitimate change.
- A conflicting submodule pointer MUST NOT be handed to a planner. It is a commit id, not three versions of a file, and the resulting patch is rejected by the validator on arrival every round. It is partitioned out exactly like Wharnex-managed project state.
- `.git` MUST be excluded from context bundles and sandbox copies whether it is a directory or a file. A submodule's and a linked worktree's `.git` is a file holding an absolute path into the host's own repository metadata.

## Exclusive-resource recovery invariant (v1.3.7)

- Wharnex MUST NEVER hold a global exclusive resource — a Git index lock, the self-evolution batch lock — in a state with no published way out. Every fail-closed condition MUST name, in the refusal itself: what is held, which operation left it there, why it stopped, and the single action that clears it. A refusal that names no remedy is a deadlock with better manners.
- A condition only an operator can clear MUST be a typed refusal, never a generic error. Generic errors reach the repair loop, which asks a planner to fix a lock file, a filesystem permission or a full disk; the round cannot succeed, the next attempt reproduces it, and the bounded budget drains against a condition no patch addresses while the verified candidate is discarded. Host Git failures in this class — a held or stale `index.lock`, refused repository ownership (`safe.directory`), an unwritable repository, a full filesystem — MUST classify as `host_working_state_blocked` and retain the candidate.
- Wharnex MUST NOT delete another process's lock to make progress. Removing a lock a live process still holds corrupts that process's write. The refusal MUST instead publish the evidence that lets the operator decide — for a lock, its path and its age, because age is what separates live contention from a crash leftover.
- A self-evolution transaction parked in a fail-closed phase MUST expose both its state and an explicit operator release. Releasing MUST name the exact transaction, MUST refuse any phase that is still active or extendable work, MUST leave the transaction directory on disk as the evidence for whatever recovery was performed, and MUST be an explicit human action unreachable from a model plan.

## Git surface invariant (v1.3.4 — see `adr/ADR-0040`)

- A project has exactly two commit modes, and the choice is Wharnex operational state stored outside the project, never in `whaness.yml` or any file the operator's own commits would carry. **Auto-commit** is the default and the historical behavior; **no auto-commit** applies the verified change and then returns the branch to the commit the host was at before Wharnex touched anything, leaving the change in the working tree.
- No-auto-commit MUST still run the full integration — pre-merge snapshot, real merge, post-merge verification — and unwind afterwards with `git reset --mixed`. Skipping the merge would reintroduce the host-drift failure `adr/ADR-0035` removed. The unwind target is the HEAD captured before the pre-merge snapshot, so the operator's own uncommitted edits are never left committed under a Wharnex bookkeeping message.
- The planner-authored `commit_message` MUST survive the unwind. Every integrated candidate is recorded — message, declared paths, and its own bracketed diff — durably and *before* the branch moves, with a partial write rolled back, so a crash leaves recoverable committed history rather than an unexplained dirty worktree whose messages are gone.
- Selective committing MUST be validated, not merely offered. Committing a path takes its current working-tree content, which already contains every earlier change to that path, so a selection that would fold an earlier unselected record into a later one MUST be refused with the blocking records named. A record whose paths no longer differ from HEAD is retired; discarding a record MUST only ever remove Wharnex's note, never touch a file.
- A commit made from the Git surface is the operator's own contribution: it uses their configured Git identity and runs their project hooks, unlike every commit Wharnex makes internally. A repository with no configured identity MUST be reported, never silently attributed to a bot.
- Push is an explicit human action requiring an explicit confirmation at the API boundary, and MUST NEVER be reachable from a model plan. Force-push MUST NOT be offered. A rejected push is an ordinary merge, not a failure: Wharnex fetches, merges and pushes again, and after an AI-assisted conflict resolution it MUST NOT push again on its own.
- A conflicting push integration or branch merge MUST be aborted before returning, with its three merge sides recorded. Leaving a conflicted merge in place would block every Agent request on the project, because Wharnex's own integration refuses to act on a repository with unresolved paths. The resolution is replayed into the same merge: merge again, check out *our* clean version of each conflicting path — a file with conflict markers is not patchable — apply the resolution patch, and commit.
- `harness.conflict/v1` carries `origin` (`integration` | `push` | `branch_merge`) plus, for the Git origins, the merge to replay. A Git-origin resolution is applied directly to the host merge and MUST NOT route through Protected verification: its product is one inspectable merge commit the operator asked for, and the planner's authority is already narrowed to the capsule's conflicting paths. It remains bounded by the same conflict-attempt budget.
- Self-evolution MUST always commit, whatever the project setting: its transaction rollback, activation and lineage anchor on real commits. The override MUST be published and the UI MUST present the toggle as fixed rather than offering a control Apply would ignore.

## Wave convergence invariant (v1.3.5 — see `adr/ADR-0041`)

- One Main Request may need several waves, and each wave MUST begin from the consolidated conclusions of every earlier wave rather than from the latest failure alone. Wharnex MUST carry a `harness.attempts/v1` ledger on every continuation, and the planner MUST return `attempts/ledger.md` in every response bundle.
- The ledger has two halves with different authorities. Wharnex measures each round itself — request id, iteration kind, plan id, closed-set outcome, argv with exit codes, one actionable detail — and that measurement is authoritative: a failed round MUST reach the next request whether or not the planner recorded it. The planner's narrative is a full replacement each round, never a delta, and its "Does not work locally" section is a hard exclusion list stating symptom, cause and the round that proved it.
- The ledger is session scaffolding, not project truth. It is discarded at the Main Request's terminal boundary, and the round Wharnex expects to be the last MUST be told so and MUST consolidate durable lessons into `harness.knowledge/v2` before that boundary.
- Every continuation request MUST carry a `harness.context-delta/v1` report measured against the **root** request's anchored base, naming exactly which paths diverged and carrying the real diff when it fits the transport budget. An unchanged project MUST be reported as an affirmative `UNCHANGED` verdict and an unmeasurable one as `UNKNOWN`; reporting an empty change list for a divergence Wharnex could not measure is forbidden.
- Every continuation MUST anchor its own request base alongside its context snapshot, so base-rooted integration applies to correction rounds and not only to Main Requests.
- Both artifacts exist to make the NEXT round cheaper and MUST NEVER cost the current one. A missing, oversized or unmeasurable artifact is a structured degradation event; it MUST NOT reject a bundle, discard a verified payload, consume a repair round, or fail a request. Attempt-ledger staging MUST remain independent of knowledge staging.

## Project knowledge storage invariant (v1.3.5 — see `adr/ADR-0042`, amending `adr/ADR-0028`)

- The local Wharnex database is the single authoritative store for project knowledge. Wharnex MUST NOT write `.wharnex/knowledge/` and MUST NOT read it as a store. A project still carrying those pre-migration files adopts them into the database exactly once, local records winning; adoption is one-way and idempotent. The subtree remains excluded from context bundles, request bases, plan patch paths and planner conflict capsules.
- Knowledge crosses machines only through an explicit `harness.knowledge-export/v1` transfer. Content MUST be verified against its recorded SHA-256 on import. A selective export MUST be marked as such and MUST NEVER be accepted as a `replace`: it does not describe the records it omits, and its absences are not deletions. Every import MUST report what it added, replaced, kept, removed and skipped.
- Clearing the catalog, wholly or selectively, requires explicit confirmation at the API boundary and MUST NOT be performed implicitly as part of another operation.
- Consolidation is catalog maintenance, not development. It reads the durable catalog alone — never a staged candidate — reuses `harness.knowledge/v2` `mode=replace` so it inherits that path's compare-and-swap and validation, commits on ingestion because it has no execution and therefore no terminal boundary, and MUST NOT alter the task's `State`, `Plan`, `Policy` or `LastExecution`. An empty consolidation result MUST be rejected: reorganizing is never a way to discard knowledge.

## Project-scoped browser-agent queue invariant (v1.3.6 — see `adr/ADR-0044`)

- One durable browser-agent queue serves every project, and a browser-agent task's owning project is its canonical absolute host project path — the same identity a workspace chat and a session carry. A ChatGPT project display name is a remote presentation label the operator can rename from ChatGPT's own UI and MUST NEVER be stored as `project_id`.
- Attribution MUST be resolved by the store at enqueue rather than trusted from each caller: a supplied absolute path is kept, any other value is discarded, and the store then resolves the task's own `chat_id` to its workspace chat's project and failing that its `session_id` to its session's project. A task that resolves to nothing keeps an empty `project_id`, belongs to no project, and is therefore hidden from every project view and blocked by no project scope.
- Every project-scoped view MUST show only its own project's tasks, and its counters MUST be computed from the same filter as its cards. A project MUST NEVER display another project's chats, request ids or lineage. Work belonging to other projects MAY be reported only as an aggregate count, because the operator needs to know the shared pool is busy elsewhere without being shown what it is busy with.
- The Supervisor/Worker pool stays global to the authenticated Desktop process and is shared across projects; it MUST NOT be multiplied per project. What is scoped is the claim: a Worker MAY claim a task only when the caller did not scope by project, or the task has no project attribution, or the task's project is currently open in some window, or the task is account-lifecycle work. Scoping MUST be enforced by the durable claim, never by claiming and releasing — a claim charges an attempt, so releasing after the fact spends the task's own retry budget on a decision that had nothing to do with the task.
- A queued ChatGPT task MAY be pinned by the operator to one canonical Worker id (`worker-N`). The durable claim MUST enforce that pin before charging an attempt, so another Worker cannot steal routed work. The operator MAY also mark that task for task-scoped **Keep flowing**: this is distinct from the persistent global/per-Worker policy, remains associated with that durable task across `WAITING`/re-claim cycles, and MUST release when that task settles terminally (`done`, `attention`, `failed`, or cancellation). A live `LEASED`/`RUNNING` task may adopt task-scoped Keep flowing only for its current lease-owning Worker; it MUST NOT be reassigned underneath another Worker. Multiple queued tasks may be pinned to one Worker, but that Worker remains single-flight and executes only one at a time.
- Provider-facing Worker navigation and autonomous submission MUST share one process-wide pacing gate. Every next Worker provider action MUST start at least 10 seconds after the previous one, including immediately after a global suspension resumes; durable 429 pressure MAY widen the gap further. Separate navigation/submission clocks are insufficient because they allow one class of action to burst immediately after the other.
- Account-lifecycle work (`ORGANIZE_CHAT`, `RENAME_CHAT`, `ARCHIVE_CHAT`, `DELETE_CHAT`, `DELETE_BUNDLE`, `DELETE_TEMP_CHAT`) is the deliberate exemption: it acts on the ChatGPT account rather than on the project, and the chat-deletion convergence rule above requires it to reach the remote conversation, its temporary sibling and its library bundles whatever is open. Every other type is request-bound project work and waits for its project.
- Closing a project MUST admit nothing new and interrupt nothing already leased, exactly as lowering per-project execution concurrency drains rather than aborts.
- An agent occupied with a task from a different project than the surface displaying it MUST say so and name that project, or a panel reporting no free Workers shows the operator only cards that look idle. It MUST expose that project's identity and nothing else about its task.

## Execution environment disclosure invariant (v1.3.1, evolved)

- Every planner request MUST carry a Wharness-measured `wharness.environment/v2` manifest describing the host machine, the Protected container's real limits, separate `sandbox_tools` and `host_tools` executable inventories with successful version probes, the policy engine's closed decision sets, and the protocol validator's numeric budgets. Legacy `tools` is only an alias of `sandbox_tools`. Policy and budget values MUST be read from the engine and validator rather than restated, so the published contract cannot drift from the enforced one.
- The manifest is descriptive only. It MUST NOT grant a capability or relax a check; policy, protocol validation and the runner remain the sole enforcement points. Measurement MUST be best-effort and time-bounded: an unavailable Docker daemon degrades the section to a warning and never delays or fails a request.
- The runner image MUST describe its own toolchain through a dedicated inventory entrypoint. A path-only shim whose version command fails MUST NOT be advertised as installed. Wharness MUST NOT maintain a parallel sandbox list; host/control tools are probed independently because post-merge gates run there.
- An infrastructure or bookkeeping fault MUST NOT consume an automatic AI repair round, and MUST NOT discard a verified executable payload. A verification infrastructure failure (missing executable, package-registry/DNS acquisition failure, resource exhaustion) MUST be classified before baseline comparison and MUST NEVER be converted into candidate success merely because the unchanged baseline hits the same infrastructure fault. Artifact archival and project-knowledge staging are auxiliary to a response bundle: their failure is recorded as a structured degradation event and ingestion continues.
- Post-merge host verification runs in Wharnex's own control container, not in the runner image the same gates were verified in, so the two environments MUST be treated as possibly unequal (see `adr/ADR-0043`). A gate that environment cannot run at all — proven by the failing command's own output: exit 127 with a missing-executable marker, or a build driver reporting the requested mode unavailable (cgo disabled, no C compiler, an unsupported instrumentation mode) — returns no verdict about the merge. It MUST be recorded as unverified on host through `integration.verification_unsupported` and named in the terminal `host.applied` event, and integration MUST continue on the Protected verdict rather than revert a verified candidate into a repair round no patch can satisfy. That classification MUST stay narrow and fail closed: an ordinary failure, a detected data race, a compile error or a runner error still reverts the host. Skipping is a fallback, not the intent — the control container's toolchain MUST be kept wide enough to run the gates the hosted projects declare, and Wharnex MUST NOT keep a parallel inventory of installed tools to make this decision.
- A repairable environment failure MUST name its root cause in the repair request. A missing executable is reported as such, never as raw command output that invites re-reading unrelated project source. Execution plans SHOULD declare ordered acquisition strategies for dependencies/tools that may be absent; sandbox lockfile hydration may be engine-owned and automatic, while host install/update/configure strategies are never automatic and remain explicit-approval boundaries.

## Bundle-only provider protocol invariant (v1.3.8 — see `adr/ADR-0052`)

- Every exchange with the model provider MUST be a bundle in both directions: exactly one logical request archive out and exactly one response bundle back. The logical request is uploaded unchanged as one ZIP when it fits the configured per-part transport limit; otherwise Wharnex transports that same archive as one canonical main part plus ordered continuation ZIPs whose payload bytes reconstruct it exactly. No other format or convention is a valid way to ask the provider for something or to accept its answer. A bare attachment, a bare file, or an answer in prose is refused, never repaired.
- A logical request archive MUST carry its own protocol identity in a root transport document, the authoritative instruction as a file inside it, and every input the exchange needs. Composer text stays a bounded bootstrap — protocol entry and the canonical expected output filename — and MUST NOT carry the request body, the instruction or the inputs. When multipart transport is required, that bootstrap also declares the exact part count and instructs the consumer to order the part manifests, concatenate their payload chunks, verify the reconstructed byte count and SHA-256, and only then open the logical request archive.
- A provider request MUST NOT depend on a tunnel (see `adr/ADR-0074`). Preparing, uploading, submitting, resending or commenting on a request MUST NOT publish to, wait for, or link any tunnel, and neither the request archive nor its composer bootstrap may carry tunnel endpoints; the archive is the only channel for context. Tunnels serve only the paired remote webapp until a tunnel-context strategy is decided in its own ADR. The local half of a submission — fetching inputs, writing the logical archive and persisting it — MUST run under an explicit bounded deadline and fail as a retryable attempt that never reached ChatGPT, rather than hold a Supervisor lease on an implicit socket timeout.
- A response bundle MUST be named by an exact canonical filename derived from that exchange's own durable identity, MUST carry its own protocol identity in a root manifest, and MUST be validated fail-closed before any byte of it is used. Validation MUST bind the answer to the request that asked for it — its identity, what was asked of it, and the digest of what was sent — because an answer that cannot be tied to its request is an answer nothing can check.
- The engine that builds a request MUST be the engine that validates its response, and a transport worker MUST NOT compose instructions or parse bundles. A contract assembled on one side of a boundary and enforced on the other drifts out of agreement with itself while every structural check still passes; that is what left translation jobs waiting in the queue with nothing to reject.
- Every response bundle is parsed under one structural boundary: relative, normalized, traversal-free entry names; no symlinks; bounded entry count; bounded compressed and expanded size; unknown fields refused in canonical manifests. Provider output is untrusted data in every exchange.
- The narrow, named exceptions are the account-management operations, which act on ChatGPT's own account objects and produce no artifact, and the temporary-title conversation, which derives its answer from ChatGPT's own conversation label rather than from a produced artifact. Legacy non-bundle shapes stay parseable only for an already in-flight request checkpointed under one; nothing new is requested in them.

## Composer directive and cross-project authority invariant (v1.3.10 — see `adr/ADR-0053`)

- `@file`, `@ref`, `@attach` and `@see` share one grammar, implemented once and consumed by both the renderer that paints them and the engine that resolves them. Two implementations of one notation is two dialects waiting to disagree about what the operator wrote. `@ref` and `@attach` additionally accept alternate typed keywords (`@reference`/`@references`/`@project`; `@att`/`@attch`/`@attche`/`@attaches`/`@attahes`/`@dir`), and `@see` accepts `@look`, all drawn from one keyword table each side builds its regex/menu from, so a spelling accepted by one can never be silently rejected by the other; the canonical form written back always uses the one primary keyword regardless of which alias produced it. Typing `@` alone, before a keyword is complete, MUST offer the available directive kinds themselves rather than require the operator to already know one. `@file` resolves through the safe whole-project explorer and may name either one file or one directory; submitting it creates only a request-local include override for that exact path plus the directory subtree, never a persisted project-config change, and mandatory exclusions, `.harnessignore`, secret detection, binary/content filtering and size bounds remain authoritative. `@see` is only an inline spotlight: it may resolve the source forms `file`, `chat`, `lib`, `ref`, `attach` and `upload` (plus legacy `project` and bare-upload forms), reuses the selected source's existing transport when bytes are needed, grants no additional write authority, and MUST NOT create a separate reference thumbnail or independent submission state.
- A directive MUST stay at the position it was written. Position is the meaning, and Wharnex MUST NOT lift a marker out of the sentence and re-list it; it adds only a bounded legend for the notation the prompt actually used. What travels is the canonical `@{[file]…}` / `@{[ref]…}` form, and canonicalization MUST be idempotent so a re-submitted prompt means the same thing twice.
- A malformed near-miss is prose and MUST be left alone. `@file:/etc/passwd` is not a directive with a bad value, and supplying one is how a traversal becomes a resolved path. Directive values are bounded, brace-free, and a project is named by a directory basename, never by a path.
- Referring to a project and changing it are separate authorities with separate sets. A `@ref:` name resolves against every project Wharnex has worked on before, open or closed, and a resolved project whose context is not attached MUST have it brought in — a reference the model cannot see is not a reference. A **change** additionally requires that project to have a live session, because the session carries the Protected/Unprotected/Full and Auto/manual modes deciding how a change reaches that host; a closed project has chosen nothing, and a fresh session's defaults are not the operator's decision to inherit on their behalf. The prompt MUST name which granted projects a change cannot reach. The composer's own `@ref` suggestions MUST be drawn from this exact same resolvable set — never from only the session's already-attached related projects — so a name the menu offers and a name the engine will actually resolve at submit time can never disagree.
- A request may change a project other than its own **only** because that request's own main prompt named it with `@ref:`. The grant is derived before the planner is asked, recorded durably against the root request, and inherited unchanged by continuations. Nothing a response returns may widen it.
- Cross-project work travels as `cross_project` in `plan.json`: one self-contained entry per project, each carrying its own mandatory `commit_message`, `operations` and `verification`, validated exactly as the primary plan is. Authorization is fail-closed at ingestion — before Policy, before any sandbox — so an ungranted project, a missing grant, duplicate entries for one project, or a target that is closed or holds unfinished work of its own cost one re-request instead of a discarded verified candidate. A closed or busy target is a typed local condition and MUST NOT reach the repair loop.
- A granted entry MUST execute as a derived request on its own project: that project's Protected sandbox, its verification, its Git-native host integration, rooted on a request base captured in that project when the prompt was submitted. Writing to a project is that project's authority and does not change because the patch arrived through another project's chat. The target project's own Protected/Auto modes decide what follows; entries run only after the primary project's work has settled, in order, stopping at the first failure, with every outcome reported including those never attempted.

## External attachment invariant (v1.3.8 — see `adr/ADR-0053`)

- `@attach:<absolute path>` names a file or directory outside every project. The path MUST be absolute and MUST NOT be repaired: a traversal, a symlinked root or a bare filesystem root is refused, never normalized into something readable.
- Wharnex MUST refuse roots where an explicit operator gesture is not sufficient justification — system and kernel surfaces, credential stores, and the bare home and filesystem roots. One typo in a composer must not be able to put an SSH key into a prompt.
- Attached material is read-only by construction. It lives under its own `ATTACHMENTS/` namespace, never inside the primary tree, and MUST NOT appear in any operation, `impact_files` entry or `cross_project` entry. It has no root a patch could be applied against, and the prompt states that alongside the listing.
- Selection MUST reuse the engine the project's own context configuration uses — mandatory exclusions, automatic pruning, include whitelist, exclude list, secret-content scan, binary detector — so one predicate governs both and neither can drift. A directory's selection travels inside its own marker, so the prompt text remains the whole state across storage, continuation and transcript.
- Every attachment is bounded in file size, total bytes and file count. Truncation and refusal MUST be reported in the prompt; an attachment that silently arrives incomplete is worse than one that never arrived.

## Manual plan transport normalization

- Manual ChatGPT import may normalize only narrowly defined transport mistakes before strict protocol validation.
- It may repair unescaped source-code double quotes only inside a `patch` value that is clearly a supported patch dialect and is structurally followed by the operation `command` field.
- Never broaden this into a general "best effort" parser that invents operations, paths, commands, protocol values, or security-sensitive semantics.
- Every normalized plan MUST still pass `protocol.Validate` and the policy engine unchanged.

## 10. Project bootstrap and context configuration (v1.2.17)

- Desktop project selection MUST use a narrow native directory-picker IPC; remote ChatGPT content never receives this capability.
- Human project creation and Git clone are explicit bootstrap actions, separate from Agent execution. Git clone MUST use argv execution and `--recurse-submodules`; it MUST NOT accept option-like repository values or overwrite an existing destination.
- Every opened/created/cloned project MUST contain `whaness.yml`. When absent, Wharness creates a safe default before context capture.
- `whaness.yml` context include/exclude settings affect AI context assembly only. They MUST NOT weaken secret/path/symlink protections or silently expand Agent/terminal privileges.
- Automatic context pruning SHOULD remove dependencies, VCS/IDE metadata, caches, generated build/test output, temporary files, archives, binary/media assets, and generated Wharness context snapshots while retaining source/configuration files by default.
- Every opened/created/cloned project MUST contain a root `CHANGELOG.md`; Wharnex creates a minimal default when absent, exactly like the `whaness.yml`/`VERSION` self-heal above. A workspace chat that begins reserves its own uniquely anchored `CHANGELOG.md` heading through a serialized, Wharnex-authored internal commit — never through the ordinary planner `apply_patch`/merge pipeline — so concurrent chats on the same project own disjoint regions of the file instead of colliding on it every Apply; the chat's archive path removes that reservation again only while it still holds nothing but Wharnex's own placeholder. Only the content a planner writes under its own already-reserved heading is an ordinary planner-authored, Policy/sandbox/merge-governed patch. See `SoT/AI_PROTOCOL.md` and `adr/ADR-0068`.

## 11. Host-independence / containerized tooling invariant (v1.2.45)

- Lifecycle, build, maintenance, and cleanup tasks (including `make build`,
  `make clean`, and any in-app administrative/cleanup feature) MUST run their
  actual work inside a container rather than depend on a tool being installed
  on the operator's host, even when that tool happens to be present.
- When a task genuinely needs a client/CLI that has no containerized
  equivalent already in the stack, add it to a project-owned tools image
  (or reuse an already-running service's own embedded binary, e.g. invoking
  `mc` inside the `minio` container itself) rather than shelling out to a
  host-installed binary. Creating a dedicated tools image is an acceptable
  and preferred cost for this.
- This exists to maximize portability across developer machines and CI: a
  host-dependent script silently breaks on any machine missing that
  particular tool version, while a containerized one behaves identically
  everywhere Docker runs.
- This does not apply to `docker`/`docker compose` themselves, or to
  editing files directly on the host filesystem — only to auxiliary CLIs a
  task would otherwise assume are present on `$PATH`.
- Narrow, explicit exception: a human-invoked `make build`/`make deps` runs
  `npm ci` for `services/frontend`/`services/desktop` directly on the host
  (containerizing that install is tracked separately, not yet done). Node
  version compatibility for that path MAY be self-healed by driving the
  operator's own already-installed `nvm`, never by installing nvm itself or
  mutating anything outside the operator's existing nvm-managed Node
  versions, and only ever as a fallback after the Node already on `PATH` is
  checked and found too old. This is deliberately host-side: nvm is
  inherently a per-user host tool with no meaningful containerized
  equivalent for *this* purpose (selecting which Node an interactive
  operator shell uses), unlike the auxiliary CLIs this section otherwise
  requires containerizing. A self-evolution build is unaffected either way:
  it runs `make build-stage` inside the backend's own container and is
  satisfied directly by that image's pinned Node.
- Context inspection MUST derive final inclusion from the current manifest/ZIP snapshot, expose structured exclusion reasons and effective rules, and never claim a file is included merely because its parent directory is eligible.
